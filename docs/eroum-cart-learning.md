# 이로움 장바구니 담기 시험 절차 (학습 기록)

범위: 이로움(https://eroumcare.com/) 로그인부터 장바구니 담기까지를 시험했고, section 12에서 주문서 화면 읽기와 시험 상품 삭제를 추가했다. 주문서 입력, 배송지 입력, 주문 확정, 결제는 하지 않았다. 자동화 코드는 만들지 않았다.

## 1. 실행 환경
- 브라우저: Aside CLI `aside repl`, 계정 선택 `--account u1` (u0은 로그아웃 상태여서 u1 프로필 사용).
- 다른 탭은 건드리지 않고 `openTab()`으로 새 탭만 연다.
- 한 번의 `aside repl` 호출은 하나의 세션이다. `page` 변수는 호출 사이에 이어지지 않으므로 한 호출 안에서 탭 열기, 조작, 확인을 함께 한다.
- 이 세션에서 `fs.readFileSync`와 `fs.mkdirSync`는 쓸 수 없다. 스크린샷 저장 경로도 CDP 타임아웃이 났다.

## 2. 로그인 절차
1. `https://eroumcare.com/` 를 연다. 상단 `로그인` 링크를 누르면 `/bbs/login.php`로 이동한다.
2. 폼 구성: 아이디 입력(`아이디`), 패스워드 입력(`패스워드`), 자동로그인 체크박스, 눈 아이콘 이미지(보안문자 아님), `로그인` 버튼.
3. 값은 `vendor-site-logins.md`의 THK 행에서 읽어 채운다. 값은 로그와 문서에 남기지 않는다.
4. 1회 제출로 로그인에 성공했다. 추가 인증이나 캡차는 나오지 않았다.
5. 로그인 후 상단에 `로그아웃`과 `사업소 장바구니 N 건`이 보인다. 시험 시점 장바구니는 0건이었다.

## 3. 상품 페이지 절차
- 상품 경로: `https://eroumcare.com/shop/item.php?it_id=<상품코드>`. DA-006은 `PRO2022042900001`이다(`worker/order-runner/src/index.ts` 매핑과 동일).
- 상품 페이지에는 `색상` 선택 목록(`select#it_option_1`, 옵션 `초록`, `회색`)이 있다.
- 버튼은 두 개다. `상품주문`은 주문 경로이므로 누르지 않는다. `장바구니`는 form `fitem`의 submit 버튼이다(같은 이름의 숨김 버튼이 하나 더 있다).

## 4. 시험에서 확인된 결과
- `selectOption({label:'회색'})`로 값을 고르면 스냅샷에는 `회색 (selected)`으로 보인다.
- 그래도 `장바구니`를 누르면 페이지 알림 `선택옵션을 선택해 주십시오.`가 뜨고 담기지 않는다.
- `change` 이벤트 강제 발생, jQuery trigger, 키보드(ArrowDown+Enter) 선택을 시도했지만 옵션 목록(`#sit_sel_option`류)이 생기지 않았고 `it_option_1` 값은 비어 있었다.
- 담기 시도 전후 `사업소 장바구니`는 0건으로 유지됐다. 장바구니는 변경되지 않았다.

## 5. 미해결 항목
- 옵션 선택이 페이지 스크립트에 반영되지 않는 원인은 아직 모른다. 수량 입력칸도 나타나지 않았다.
- 실제 마우스 클릭으로 옵션 목록을 열어 선택하는 방법, 또는 다른 진입 경로(검색 결과, 목록)에서 담기를 시험해야 한다.
- 스크린샷 저장은 아직 되지 않았다(`.local-analysis/eroum/`에 파일 없음).

## 6. 추가 시험 (실제 마우스·키보드 입력)
- 통한 방법(옵션 선택): 색상 `select#it_option_1`을 실제 마우스 클릭으로 열고, 키보드 ArrowDown 두 번과 Enter로 `회색`을 고르면 옵션 행(`li.it_opt_list`, "색상:회색")이 생긴다. 수량 입력칸(`ct_qty`)은 1로 채워졌다. `selectOption` 강제 선택과 `change` 이벤트 강제 발생은 행을 만들지 못했으므로 이 방법은 쓰지 않는다.
- 옵션 선택 후 장바구니 담기 시도(실패): (1) 장바구니 버튼으로 실제 마우스 클릭, 버튼이 뷰포트 아래에 있어 마우스 휠로 스크롤한 뒤 클릭, 히트 테스트로 버튼이 맞는지 확인, (2) 같은 버튼에 포커스를 준 뒤 키보드 Enter. 두 경우 모두 네트워크 요청(`itemcart.php`)이 나가지 않았고, 알림창·확인창도 뜨지 않았다. 폼 검증(`it_price`, 옵션 행, 수량)은 읽기 전용으로 확인했을 때 모두 통과 상태였다.
- 원인은 아직 모른다. 제출 핸들러가 호출되지 않는 것으로 보인다.
- 시험 종료 시점 `사업소 장바구니 0건`이 유지됐다. 주문하기 버튼은 누르지 않았다.
- 읽기 전용으로 확인한 제출 함수: `fitem_submit`은 장바구니 경로에서 `./itemcart.php`로 POST한다. 이 경로에 도달하지 못했다.

## 7. 정정 (재시험 기준, 2026-11-06)
- 앞선 "담기 실패, 0건" 결론은 정정한다. 이전 시험에서 실제로는 DA-006이 장바구니에 담겨 있었고, 사용자가 삭제했다(코디네이터 전달 내용). 따라서 "담기 실패"는 맞지 않는다. 담긴 것을 화면 표시(`사업소 장바구니 N 건`)로 판단하면 틀릴 수 있다.
- 담기 버튼은 `$.post('./itemcart.php')`로 페이지 이동 없이 요청하고, 완료 후 확인창(confirm)이 뜬다. 자동화 도구가 창을 자동으로 닫았을 수 있으므로 dialog 이벤트를 켜 두고, 결과는 `cart.php`를 직접 열어 확인한다.
- 옵션 선택 방법(section 6): `select#it_option_1`을 실제 마우스로 클릭해 목록을 연 뒤 ArrowDown 두 번과 Enter로 `회색`을 고르면 `li.it_opt_list`에 `색상:회색` 행이 생겼다(재시험에서 재확인).

## 8. 다품목 담기 절차 (상품마다 반복, 수량 1)
1. 시작 전 `https://eroumcare.com/shop/cart.php`를 열어 비어 있는지 확인한다. 비어 있지 않으면 아무것도 담지 않고 멈춘다.
2. 상품 상세(`shop/item.php?it_id=<상품코드>`)를 연다. 옵션이 있으면 section 6 방법으로 고른 뒤 `li.it_opt_list` 행이 생겼는지 확인한다.
3. 상품 상세 페이지에서 dialog 이벤트와 `itemcart.php` 요청·응답 기록을 켠 뒤, `장바구니` submit 버튼(`input[type=submit][value="장바구니"]`)을 정확히 한 번 누른다. `상품주문` 버튼은 누르지 않는다.
4. 응답이 안 보여도 재클릭, 재시도, Enter 재입력을 하지 않는다. 같은 REPL 호출 안에서 `cart.php`를 열어 상품명, 색상, 수량을 확인한다. 1건이 확인되면 다음 상품으로 넘어간다.
5. 예상과 다르면 추가 조작 없이 멈추고 보고한다.

## 9. 재시험 결과 (2026-11-06)
- 로그인: 이미 로그인된 `u1` 프로필을 사용했다(로그인 과정은 수행하지 않았다). 장바구니 시작 상태는 0건, 비어 있음이었다.
- DA-006 회색 옵션 선택은 성공했다(`색상:회색` 행 확인).
- 장바구니 버튼 클릭 시도는 `Node is not an Element` 오류로 끝났다. 클릭이 전달되지 않은 것으로 보이며, 이후 `cart.php`는 여전히 비어 있었다.
- DYJ-03은 시도하지 않았다. 캡처 `.local-analysis/eroum/cart-after.png`도 저장하지 않았다. 따라서 이번 재시험은 완료되지 않았다.
- 주문하기·상품주문, 주문서 작성, 결제, 배송지 입력, 주문 확정은 하지 않았다. 장바구니 상품을 수정하거나 삭제하지 않았다.

## 10. 허용된 1회 재시도 결과
- 재시도 전 `cart.php`는 비어 있었다. 상품 페이지를 새로 열고 DA-006 회색 옵션 행(`색상:회색`)을 다시 만들었다.
- `form[name=fitem]`의 `장바구니` 버튼 개수 확인 단계에서 DOMException이 났다. 확인 단계에서 멈췄고 장바구니 버튼은 누르지 않았다(로그에 count 결과가 없음).
- 재시도 후 `cart.php`는 여전히 비어 있었다. 1회 재시도 허용이 소진됐으므로 DYJ-03과 `cart-after.png`는 진행하지 않았다.
- 원인(셀렉터 `:visible` 또는 locator 확인 단계)은 아직 확정하지 못했다. 다음 시험에서 `form[name=fitem]` 버튼을 `evaluate`로 읽어 확인하는 방식이 필요하다.

## 11. 성공 기록 (2026-11-06, 이어받기)
- 시작 전 `cart.php`는 0건이었다. 상품 상세에서 `evaluate`로 `form[name=fitem]`의 보이는 `장바구니` 버튼을 읽어 값과 일치를 확인했고(`상품주문` 아님), `elementFromPoint`로 클릭 지점이 그 버튼임을 확인한 뒤 `page.mouse.click` 좌표 클릭을 정확히 한 번 했다. 이전 실패(`Node is not an Element`, 버튼 개수 확인 DOMException)는 locator 방식 때문으로 보이며, 이 좌표 방식은 통했다.
- DA-006: 옵션은 section 6 방법으로 `색상:회색` 행 생성 후 담기. DYJ-03(`PRO2022102700012`): 옵션 없음, 기본 수량 행 1개 상태에서 담기.
- 결과: `cart.php`에 `사업소 장바구니 2건` — DA-006 색상:회색 1개, DYJ-03 1개. 다시 누른 상품 없음.
- 이번 시험에서는 `page.on('dialog'/'request')` 기록이 비어 있었다(이벤트가 잡히지 않음). 담김 여부는 `cart.php`로 확인했다.
- 스크린샷 `.local-analysis/eroum/cart-after.png`는 CDP 타임아웃으로 저장하지 못했다(두 번 시도). 지휘자가 `cart.php`를 읽기 전용으로 다시 열어 두 상품, 색상, 수량 1을 직접 확인했다.
- 주문·결제·주문서·배송지·수정·삭제는 하지 않았다. 이 시점에는 장바구니 2건을 남겨 두었고, 이후 section 12에서 삭제했다.

## 12. 주문서 화면 구조와 장바구니 삭제 (2026-11-06, 주문 없음)
사용자 승인 범위는 주문서 화면을 열어 읽는 것과 시험 상품 삭제까지다. 입력, 저장, 최종 주문 버튼은 쓰지 않았다. 아래 값은 구조만 기록했고 실제 주소, 연락처, 금액은 넣지 않는다.

### 주문서로 이동
- 장바구니 `주문하기`(`button[onclick="return form_check('buy');"]`)는 `form[name=frmcartlist]`를 `cartupdate.php`로 `act=buy` POST한다. 폼에는 장바구니 값만 있고 배송지·결제 값이 없다.
- 이동한 화면은 `shop/simple_order.php?od_id=<번호>`이고 제목은 `주문신청`이다. 이 `od_id`는 짧은 숫자이고, 주문내역의 주문번호 형식과 다르며 주문내역에도 나타나지 않았다. 이동한 뒤에도 장바구니 2건은 그대로였다.
- 비유통·품절 상품이 섞이면 주문 전 안내창(`#pop_sup1`~`#pop_sup4`)이 뜨는 분기가 스크립트에 있다. 이번에는 뜨지 않았다.
- 주문서 페이지에는 떠날 때 `ajax.simple_order.php`로 `clean=ok`를 보내는 `beforeunload` 처리가 있다. 같은 주소를 다시 열면 상품 없는 빈 양식이고 `주문하기`가 비활성이며 배송 영역이 숨겨진다. 다시 보려면 장바구니에서 다시 들어가야 한다. 자동화에서 주소를 저장해 재사용하면 안 된다.

### 주문서 구조 (`form#simple_order`, `name=forderform`)
| 영역 | 요소 | 비고 |
| --- | --- | --- |
| 주문 구분 | 라디오 `pen_type` (`일반주문`, `수급자 선택 후 주문`) | 기본 `일반주문` |
| 상품 추가 | `#ipt_so_sch`, `.btn_so_sch`(`상품검색`) | 이 화면에서도 상품을 더할 수 있다 |
| 상품 행 | `io_id[]` 옵션 선택, `prodMemo[]` 상품 요청사항, `ct_qty[]` 수량, `감소`, `증가`, `.btn_del_item`(`삭제`) | 요청사항은 품목별 칸이다 |
| 배송지 방식 | `.order-info .top`의 `신규 배송지`, `배송지 목록`(`#order_address`), `수급자 목록`(`#pen_address`) | 누르지 않아 목록 안 구성은 모른다 |
| 받는 곳 | 이름 `od_b_name`, 전화 `od_b_tel`, 휴대폰 `od_b_hp`, 우편번호 `od_b_zip`, 주소 `od_b_addr1`, 상세주소 `od_b_addr2`, 요청사항 `od_memo` | 처음 열면 이름, 전화, 휴대폰, 주소가 이미 채워져 있다. 우편번호와 주소 칸은 읽기 전용이고 `우편번호` 버튼으로 고른다 |
| 숨은 주문자 칸 | `od_name`, `od_tel`, `od_hp`, `od_zip`, `od_addr1`, `od_addr2`, `od_email` | 채워져 있고 화면에는 숨겨져 있다 |
| 배송 방식 | `od_delivery_type` (`택배(선불)`) | 숨겨진 선택 칸 |
| 매출증빙 | 라디오 `ot_typereceipt`와 세금계산서 칸 | 채워져 있고 숨겨져 있다 |
| 최종 버튼 | `button.btn_so_order`(submit), 위아래 2개, 문구 `총 N개 상품 주문하기` | **절대 누르지 않는다** |

### 주의: 주문서에 결제수단 선택이 보이지 않는다
- 관찰: 숨은 값 `od_settle_case`가 `월 마감 정산`으로 들어 있고, 화면에 결제수단 선택 칸이 없다. 폼은 `form_submit`을 거쳐 `orderformupdate.php`로 제출된다.
- 판단: `총 N개 상품 주문하기`는 주문을 생성할 수 있는 최종 제출 버튼으로 간주하고 누르지 않는다. 눌러 보지 않았으므로 실제 접수 시점과 후속 화면은 확인되지 않았다.
- 장바구니의 `주문하기`와 글자가 비슷하므로 글자에 `주문하기`가 있다는 이유로 판단하지 말고, 화면 주소와 버튼 class로 구분한다.

### 납품처별 배송지
확인한 화면에서 받는 곳 칸은 주문당 한 벌이고 품목별 배송지 칸은 보이지 않았다. 품목별로 보이는 것은 `prodMemo[]` 요청사항뿐이다. 납품처가 다른 품목은 주문을 나눠야 할 것으로 보이지만, 주문을 제출하지 않았으므로 확정이 아니다.

### 장바구니 삭제
승인된 품목을 지울 때만 쓴다.
1. `cart.php`에서 상품 행과 체크 상태를 읽는다. 체크된 모든 행이 승인된 모델·옵션·수량과 정확히 일치하고, 체크된 다른 행이 없을 때만 진행한다. 일치하지 않으면 누르지 않고 멈춘다.
2. `선택삭제`(`button[onclick="return form_check('seldelete');"]`)를 한 번 누른다. 확인창 없이 바로 제출되므로 누르기 전 대조가 필수다. 같은 폼의 `전체삭제`(`form_check('alldelete')`)는 쓰지 않는다.
3. `cart.php`를 새로 열어 대상 행이 사라졌고 대상이 아닌 행은 그대로인지 확인한다.

이번 결과: 장바구니에 승인된 DA-006 회색 1개, DYJ-03 1개만 있었고, 지운 뒤 `장바구니가 비어 있습니다.`, 행 0개, `사업소 장바구니 0건`이었다.

### 새 주문이 없음을 확인하는 법
- `shop/orderinquiry.php`를 읽기 전용으로 연다. 목록의 `od_id` 앞 12자리가 시각(`YYYYMMDDHHMM`)으로 보이며 최신순이다.
- 시험 시작 시각 이후 번호가 없는지 비교한다. 이번 시험은 18시대였고 해당 번호는 0건이었다. 상품명 글자만 찾으면 기존 주문에 걸린다. 이번에도 `DYJ-03`은 그날 14시대의 기존 주문에서 잡혔다.

### 브라우저 도구 메모
- locator 대신 `evaluate`로 버튼 글자와 `onclick`을 읽고, `elementFromPoint`로 지점을 확인한 뒤 `page.mouse.click` 좌표 클릭을 쓰면 통했다.
- `aside repl` 호출이 끝나면 그 호출에서 연 탭이 닫힌다. 화면을 이어서 읽어야 하면 이동과 읽기를 한 호출에 넣는다.
- REPL의 `fs` 쓰기는 세션 폴더(`pwd`) 안만 되고, 이 폴더는 호출이 끝나면 사라진다. 스크린샷을 남기려면 base64로 출력해 밖에서 복원해야 한다.
- 이로움 페이지의 스크린샷은 이번에도 시간 초과로 실패했다. 증거는 `.local-analysis/eroum/cart-delete-evidence.txt`에 텍스트로 남겼다.

## 13. 신규 배송지 시험 시도 (2026-11-06, 미완료)

향후 배송지 입력은 항상 `신규 배송지`로 시작한다. `배송지 목록`·`수급자 목록`은 쓰지 않는다. 받는 곳 칸 이름은 section 12의 `od_b_name`, `od_b_tel`, `od_b_hp`, `od_b_zip`, `od_b_addr1`, `od_b_addr2`, `od_memo`를 기준으로 한다. 신규 선택 후 초기화와 주소 검색 팝업 동작은 이번에 확인하지 못했으므로 추정해 구현하면 안 된다.

- 이미 로그인된 u1 프로필에서 시작했고 `/shop/cart.php`는 비어 있었다.
- DYJ-03 상세에서 기본 수량 1, 옵션 없음과 보이는 `장바구니` 버튼 좌표를 읽었다. 좌표 클릭은 정확히 한 번만 수행했다.
- 클릭 후 `/shop/cart.php`를 열었으나 비어 있었고, 다시 읽기 전용으로 조회해도 빈 문구와 상품 행 0개였다. 버튼 좌표의 y값이 977이었으나 클릭 시 화면 안 지점인지 히트 테스트하지 않아 클릭 전달을 입증하지 못했다. 사이트의 담기 실패로 단정하지 않는다.
- 중복 담기 방지를 위해 재클릭하지 않았다. 주문서 진입·신규 배송지 선택·주소 입력·주소 검색은 수행하지 못했다. 시험 상품은 남지 않았고 삭제할 항목도 없었다.
- `/shop/orderinquiry.php`에서 시험 시각 이후 주문 0건과 최신 번호 시각이 당일 14시대인 것을 확인했다. 최종 `.btn_so_order`는 누르지 않았다.
- 다음 시험은 장바구니가 빈지 먼저 확인하고, 버튼을 화면 안으로 옮긴 뒤 `elementFromPoint`로 클릭 지점을 확인해야 한다. 이번 미완료를 성공으로 간주하지 않는다.

## 14. 화면 안 클릭 재시험 (2026-11-06, 신규 배송지 시험 미완료)

- 기존 보필 신규 배송지 성공 기록은 유지하고 이로움만 이어서 시험했다. 시작 전 장바구니는 빈 문구와 상품 행 0개였다. 재시도 전에 라우터의 `retry-once` 예약을 완료했고 남은 재시도는 0회다.
- DYJ-03(`PRO2022102700012`)은 옵션 없이 기본 수량 1이었다. 첫 휠 조작 후 버튼은 여전히 화면 아래였고 히트 테스트도 실패했으므로 누르지 않았다. 마우스를 본문으로 옮겨 실제 휠 스크롤을 한 뒤, 화면 크기 1440×900에서 보이는 `장바구니` 버튼 중심이 (766.5, 326.859375)이고 `elementFromPoint`가 해당 버튼과 일치함을 확인했다.
- 이 지점을 실제 마우스로 정확히 한 번 클릭했다. 직후 상품 폼 스냅샷에서 수량·주문·장바구니 요소가 사라졌으나, 직접 연 장바구니는 비어 있었다. 이후 장바구니를 다시 읽어도 빈 문구, 상품 행 0개, DYJ-03 없음이었다. dialog 및 `itemcart.php` 요청 리스너 기록은 비어 있었으므로 실제 서버 요청 여부나 실패 원인을 확정하지 않는다.
- 불확실한 재클릭은 하지 않았다. 주문서 진입, 신규 배송지 선택과 초기화, 주소 검색, 시험값 입력은 **미완료**다. 최종 주문·결제·배송지 저장·회원정보 변경은 하지 않았다. 이 시점에는 삭제할 시험 상품이 없었다.
- 종료 확인: 양 사이트 장바구니는 각각 빈 문구와 상품 행 0개였다. 주문내역을 읽기 전용으로 확인했으며 시험일 18시 이후 주문은 양쪽 모두 0건이었다. 이로움 최신 주문 시각은 당일 14시대, 보필은 당일 09시대였다. 주문번호와 수취인 정보는 기록하지 않는다.
- 항상 신규 배송지로 시작한다는 원칙은 유지한다. 이번 결과로 이로움의 신규 선택 초기화·주소 검색·필수 검증 동작을 추정해서 구현하면 안 된다. 담기 동작이 확인되지 않은 상태에서 같은 클릭을 반복하지 않고 원인을 별도로 해결해야 한다.
