# 센터 발주 대기열

2026-11-17 사용자 결정: 전날 센터 발주서를 다음 날 아침 한 번 올리고, 하루 여러 차례 올리는 제조사 발주서의 발주처별 첫 작업에 자동으로 합친다. **이로움·안앤락은 품목이 속한 회차의 그날 첫 작업**에 합친다. 이 문서는 코드 사용법이며 운영 데이터 업로드·배포·실제 주문을 했다는 뜻은 아니다.

## 올리기

1. 운영 페이지 **센터 발주 대기열 → 센터 발주 올리기**에서 `.xlsx` 파일 여러 개를 선택한다. 파일당 10MB·5,000행 이하다.
2. 공통 열은 `주문번호`, `납품처`, `납품처전화번호`, `품명`, `주문수량`, `비고(내역)`이다. 주문번호 공란은 허용한다. 파일명에 원본 날짜가 없으면 사람이 입력한다. 원본 날짜와 업로드 날짜는 별개다.
3. 파일별 시트 이름·사용 행 수·머리글·숨김 안내를 확인한다. 보이는 시트가 한 개면 자동 선택하고 둘 이상이면 사람이 한 개를 고르기 전 저장을 막는다. 숨김 시트는 처리하지 않는다.
4. 행별 발주처·수취인·수량·보류 사유를 확인하고 **센터 대기열에 저장**한다. 공급가격표의 전체 모델명과 기존 상품 연결표로 분류하며 본체 모델 일부·파일명으로 부품 발주처를 추정하지 않는다.
5. 발주처별 목록에서 품명·센터·수량·수취인·원본 파일/날짜/시트/행·상태·작업 ID와 오늘 접수마감을 확인한다.

수취인이 비면 기존 규칙대로 비고 센터명을 우선하고 없으면 파일명 센터명을 쓴다. 후보 복수·미확정·보필 20자 초과는 보류한다. 기존 수취인은 보존하며 배송 메모는 원본 `비고(내역)`만 사용한다.

파일명·원본 날짜·시트·원본 행·납품처·품명/옵션·수량의 SHA-256 키로 재업로드·동시 업로드의 중복을 막는다. 날짜·시트가 다른 행이나 키 내용이 바뀐 수정 행은 다른 키다. 같은 날짜·업체 제조사 파일 경고와 최종 원장의 행 내용 중복 방지도 유지한다. 원본은 Firebase에만 보관하고 공개 저장소·시험에는 실제 주소·고객정보를 쓰지 않는다.

**검증 보류 행 처리:** 대기열에 `대기 · 검증 보류`와 사유를 표시하며 정상 센터 상품·제조사 작업을 막지 않는다. 같은 파일명·날짜·시트·행·납품처·품명·수량을 유지하고 연락처·비고 등 잘못된 값을 고친 파일을 다시 올리면 아직 예약하지 않은 보류 행만 한 건으로 교체한다. 검증 완료·예약·완료 행은 재업로드로 덮어쓰지 않는다. **보류 항목 제외**를 누르면 `EXCLUDED`로 남겨 자동 예약·미발주 알림에서 제외하며, 같은 행의 수정본을 올려 복원할 수 있다. 키에 포함된 납품처·품명·수량 자체를 고친 경우에는 옛 보류 행을 먼저 제외하고 수정 파일을 올린다.

발주처가 없거나 모호한 행은 **부품 주문(발주처 미정)**의 별도 `HOLD` 작업으로 묶으며 자동 실행에서 제외한다. 같은 행 재업로드는 부품 작업도 추가하지 않는다. 업체는 알지만 시간표에 없는 사과나무코퍼레이션·에이블라이크 등은 **발주 시각·방식 미정**으로 표시하며 자동 합치기·센터 단독 작업 생성은 하지 않는다.

## 합치기와 복귀

제조사 작업의 `sourceSystem`을 공급업체의 `scheduleVendor`와 시간표 앱 채널에 연결한다. **티에이치케이컴퍼니 → THK → 이로움**은 같은 채널이다. `data/item-rounds.json`의 승인된 품목·옵션을 `scheduleKey`로 연결해 이로움 오전·오후 및 안앤락 11:30·13:00·13:30의 첫 작업 이력을 각각 관리한다. 안앤락 소분류 4·5구분은 같은 13:00 회차다. 기존 같은 날 작업은 저장된 회차 키 또는 정확히 한 회차에 속하는 품목으로 확인하며 업로드 시각으로 추정하지 않는다. 회차가 섞이거나 품목이 미확정인 작업은 회차 키 없이 자동 합치지 않는다. 예전 채널 단위 이력은 다른 회차를 막지 않는다. 삭제·보류해도 해당 회차의 첫 작업 이력을 지우지 않으며 같은 회차의 두 번째 작업에는 그날 추가 업로드한 센터 상품도 자동으로 붙지 않는다.

표에 없는 품목·부품·옵션이나 옵션 미기재 품목은 **회차 확인 필요(표에 없음)** 묶음으로 표시한다. 자동 합치기·마감 알림·센터 단독 작업 생성에서 제외하며 시간이나 본체 모델로 회차를 지어내지 않는다. 해당 품목의 발주처 자체도 미확정이면 기존 부품 주문 보류 규칙을 함께 적용한다. 표는 회차만 확인하며 실제 주문 허용이나 상품·옵션 사이트 매핑을 대신하지 않는다.

회차 미확정 상품은 다른 검증이 완료된 `READY` 행이어도 **회차 미확정 항목 제외**로 대기열에서 제외할 수 있다. 제외 후 같은 원본을 다시 올려도 자동 복원하지 않는다. 품목·옵션이 표에 없으면 담당자가 대응을 확인하고 승인된 표를 갱신해야 하며 자동 발주로 우회하지 않는다. 최신 사용자 승인 표와 이전 발주처 학습값이 충돌하는 정확한 품목은 최신 표를 우선하고 `supplierEvidenceConflict`에 이전 값과 승인 값을 남긴다. 현재 확인된 충돌은 ActiveFree OP5의 이전 사과나무코퍼레이션 → 승인된 안앤락이다.

첫 작업 생성과 예약을 한 트랜잭션으로 저장한다. 검증 완료된 대기 상품만 작업 행에 넣고 대기열을 `RESERVED`와 해당 작업 ID로 바꾼다. 충돌하지 않는 실행 행 번호를 부여하되 원본 행 번호는 별도 보존한다. 동시 작업 두 개가 같은 상품을 가져갈 수 없다. 처음부터 보류·실패인 제조사 작업에는 센터 예약을 남기지 않고 남은 행의 검증 상태로 작업 상태를 다시 계산한다.

**서버 결과 검토 → 함께 포함한 센터 발주 → 빼고 대기열로 돌리기**를 누르면 행을 작업에서 제거하고 대기열로 돌린다. 이전 준비 보고·검토·내용 승인·예약 실행 정보를 무효화하므로 남은 행의 서버 준비와 검토·최종 승인을 다시 진행한다. 자동으로 다음 회차에 다시 붙이지 않으며 필요하면 센터 단독 작업을 만든다.

작업 보류·실패 시 제출 이력 없는 센터 행은 작업에서 제거되고 대기열로 복귀한다. 주문 상세의 **작업 삭제**에서 확인 후 삭제해도 같은 트랜잭션으로 복귀시킨다. 실행 중·최종 제출 대기 중·완료 작업의 삭제·센터 제외는 막는다. 실제 제출 모드에서 모든 행의 주문번호·제출 시각을 확인해 작업이 완료되어야 `COMPLETED`로 바뀐다. 준비 성공·검토 수락은 발주 완료가 아니다.

업체별 발주 현황판의 **수동 발주 완료 표시**도 연결한다. 메일·팩스·카톡·ERP·직접 B2B몰의 기존 수동 처리 업체는 사람이 외부 발주를 마친 뒤 완료 표시하면 센터도 같은 트랜잭션에서 `COMPLETED`로 바뀐다. 수동 완료를 취소하면 같은 작업 ID의 `RESERVED`로 되돌리고 대기열에 풀지는 않는다. 발주처·회차·수단·이전 상태·완료 시각·담당자와 예약 소유권을 대조하며 주문 내용 동시 변경을 금지한다. 보필·이로움에는 수동 완료 경로를 허용하지 않고 기존 승인·실제 제출 결과가 계속 필요하다. 제출 이력이나 불명확한 결과가 있는 작업도 수동 표시로 우회하지 못한다.

센터 포함 작업은 상태 전환 없이 완료 기록만 넣거나 지우는 갱신도 거부한다. 현황판의 **발주없음**은 별도 기록으로 유지하며, 센터 예약 트랜잭션과 동시에 저장되어도 ETag 재시도로 양쪽 기록을 보존한다.

복귀·제외로 현재 보고를 무효화할 때 이전 보고는 `lastReport`로 보존하며 검토 화면에 **이전 처리 결과 (읽기 전용)**로 표시한다. 보류 사유 확인에만 쓰고 검토 수락·최종 승인에 재사용하지 않는다.

기존 원장에 `SUBMITTING`, `UNKNOWN`, 일부 `SUBMITTED` 이력이 있으면 실패·보류라도 예약을 유지한다. 불명확하거나 이미 제출된 상품을 새 작업으로 돌려 중복 주문하지 않기 위한 기존 안전 규칙이다. 주문내역 확인 전 재시도하지 않는다.

## 마감과 단독 작업

한국시간 해당 품목 회차의 `receiptDeadline`(**업체 발주 마감**) 30분 전부터, 오늘 해당 회차의 제조사 작업이 없고 대기 상품이 있으면 **센터 상품 미발주**를 표시한다. 예를 들어 이로움 오후는 14:30의 30분 전인 14:00, 나래-4000/와인은 안앤락 14:00의 30분 전인 13:30이다. `orderDeadline`은 사내 주문 마감이다. 품목별 회차가 없는 업체는 기존 업체 첫 마감을 따른다. 15초마다 갱신하며 기존 시간표의 주말 준비 제외 규칙을 따른다. 마감 뒤에도 처리 전까지 표시한다. 외부 알림·메일을 발송하지 않는다.

**센터 상품만 따로 주문 만들기**는 사람이 누를 때만 선택한 발주처·회차의 검증 완료된 대기 행으로 새 `READY` 작업을 만든다. 회차별 묶음의 버튼은 해당 회차 키를 전달하며 회차가 여러 개인데 선택하지 않은 호출은 거부한다. 알림과 시간표가 있는 대기 묶음에 버튼이 있어 늦게 올리거나 검토에서 제외한 상품도 처리할 수 있다. 보류 행은 사유와 함께 대기열에 남기며 검증 완료 행이 하나도 없으면 버튼을 비활성화한다. 단독 작업은 제조사 첫 작업 이력을 소비하지 않으며 자동 실행·자동 제출하지 않는다.

## 저장과 제출 보호

| 경로 / 필드 | 내용 |
| --- | --- |
| `order-ops/center-queue/entries/{행 키}` | 원본 행·발주처·채널·업로드 날짜와 `WAITING`/`RESERVED`/`COMPLETED`/`UNASSIGNED`/`EXCLUDED` |
| `order-ops/center-queue/firstJobs/{한국 날짜_인코딩한 채널 또는 회차 키}` | 새 제조사 첫 작업 ID. 품목 회차 업체는 `이로움\|14:00`처럼 회차별 기록. 삭제해도 유지 |
| `order-ops/jobs/{작업 ID}/rows[]` | 기존 작업 행. 합친 행에 `centerQueueId`, `sourceLineNo`, `sourceDate`, `sourceWorkbook`, `selectedSheet` 추가 |
| `orderOrigin: CENTER_ONLY` | 사람이 만든 센터 단독 작업 |
| `jobs/{작업 ID}/lastReport` | 센터 복귀·제외 전의 보고. 읽기 전용 이력이며 승인 대상이 아님 |
| `entries/{행 키}/completedVia` | 수동 완료 표시는 `MANUAL`, 서버 제출 완료는 `SUBMIT`. 수동 완료 취소는 `MANUAL`만 허용 |

브라우저는 공통 부모 `order-ops`의 Firebase REST ETag/`If-Match` 조건부 PUT을 사용한다. `412` 충돌은 최신 상태로 다시 계산하고 12회 뒤 보류한다. 워커도 같은 부모에서 Admin SDK 트랜잭션으로 선점·결과를 저장한다. 부모 읽기·트랜잭션 권한이 필요하며 이번에는 운영 권한·규칙을 바꾸거나 실제 확인 요청을 보내지 않았다. 데이터 증가에 따른 부모 트랜잭션 비용·충돌은 운영 관찰 대상이다. 작업 ID는 기존 최근 큐 조회와 호환되는 시간순 Firebase push 키다.

선점 시 센터 예약 소유권과 원본 필드를 검사한다. 브라우저·Node 계획·Python 준비 모두 센터 행마다 원본 파일과 사람이 선택한 보이는 시트를 대조한다. 출처 불일치·같은 작업의 실행 행 번호 중복은 외부 요청 전에 차단한다.

센터도 **서버 준비 → 검토 수락 → 주문 확정 → 제출**과 기존 업체 제한·내용 승인·승인 30분 만료·HMAC 원장·모든 행 잠금·금액·배송비·결제·동의·신규 주소 검증을 거친다. 예약 ID·원본 행·파일/시트 목록도 내용 승인에 묶는다. 원장 키는 바뀐 실행 행 번호 대신 원본 행 번호·파일·날짜를 사용하므로 작업을 옮겨도 같은 원본을 재주문하지 못한다. 보필의 배송지 주문 한 건 제한과 이로움의 한 행 제출 제한도 유지한다.

워커 결과 저장의 갱신 콜백은 오류를 잡고 트랜잭션을 중단한 뒤 콜백 밖에서 보고하며, 미적용 트랜잭션도 성공으로 처리하지 않는다. 프로세스 종료나 예약 불일치로 `RUNNING`에 남으면 자동 재시도·잠금 해제·삭제하지 않는다. 복구 담당자가 별도 허용된 조회로 워커 종료·행 잠금·신뢰 원장·주문내역을 대조한 후, 제출 시도 없음이 확실한 경우에만 승인된 복구 절차로 상태·예약을 함께 정리해야 한다. `UNKNOWN`·실제 접수 가능성이 있으면 예약을 유지한다. 이번에는 운영 복구나 확인 요청을 실행하지 않았다.

## 검증과 남은 범위

합성 엑셀·모의 Firebase ETag 서버·모의 워커로 분류/중복, 첫/두 번째 작업, THK 연결, 제외·보류·실패·삭제 복귀, 실제 완료, 동시 예약, 마감 알림/단독 작업, 시간표 미정, 복수 원본 검사와 보필의 승인/원장/행 잠금을 시험한다. 전체 시험·빌드·타입 검사·비밀값 검사와 다른 모델의 독립 검토는 `.orca-routing/tasks/center-queue/evidence.json`에 기록한다.

운영 ETag/CORS/권한 확인, 실제 데이터 업로드·주문은 이번 허용 범위 밖이다. workflow·스위치·저장소 변수·푸시도 실행하지 않는다. 후속 지휘자 지시로 이번 작업 파일만 로컬 커밋하고 `origin/main`의 업체별 발주 현황판 변경 위로 재배치했으며 두 기능을 모두 보존했다. 시간표 미정 업체의 발주 수단·시각과 기존 사이트 상품/옵션 미매핑은 확인 과제다.
