# 직배주문 공유 작업 기록

이 프로젝트는 Orca 작업 공간 여러 개와 Claude, Codex가 함께 작업한다. 대화끼리는 서로 보지 못하므로
**이 파일이 공유 인수인계 문서**다. 작업 절차는 `AGENTS.md`의 "Shared workflow"를 따른다.

이 저장소는 공개 상태다. 비밀번호, 승인 코드, 세션, 수취인 정보, 거래처 연락처, 내부 시스템 주소는 적지 않는다.

## 최종 목표

**멤버십 직배 주문의 자동화.** 업체별 주문 수단으로 발주를 자동 처리하고, 사용자 PC가 꺼져 있어도 돌아가야 한다.

```text
주문 취합(아마란스, 현재는 사람) → 업체별 분류·마감 확인 → 운영 페이지 검토·승인
→ 업체별 실행(B2B몰/ERP/메일/팩스/카톡) → 주문번호·결과 기록 → 입출고 등록(마지막 단계)
```

주문 데이터는 **IMS 개발이 끝날 때까지 아마란스에서 가져온다(11-09 사용자 확정).** IMS가 준비되면 출처를 IMS로 바꾼다.

## 작업 공간 = 세부 작업

각 Orca 작업 공간은 위 목표를 이루기 위한 **세부 작업 하나**다. 공간의 결과물은 모두 `main`에 모여
하나의 자동화 흐름으로 이어진다. 작업할 때는 내 공간의 결과가 앞뒤 단계와 맞물리는지 확인한다.

| 공간 | 브랜치 | 맡은 단계 | 진행 상황 |
|---|---|---|---|
| main | `main` | 전체 통합. 운영 페이지, 주문 워커, 이 문서 | 공유 규칙과 이 문서 정리(11-09) |
| 발주 시간표 및 스케줄 | `rlawltn260116-byte/learn-timetable-schedule` | 업체별 마감·발주 수단, 발주 준비, 사이트 주문 절차 학습 | 11-06까지 `main`에 반영함. `docs/direct-order-learning.md`, `tools/analyze_direct_orders.py`와 시험 파일은 커밋 전 |
| 입출고 등록 | `rlawltn260116-byte/입출고-등록` | 주문 완료 후 입출고 등록. 전체 흐름의 마지막 단계 | 운영 페이지에 명세서 검수→입고·출고→재조회 절차와 보류 기준 반영. 검수 결과 연동·실제 등록 절차 확인 대기 |

새 세부 작업을 시작하면 공간을 만들고 이 표에 맡은 단계와 함께 한 줄을 추가한다.

## 반드시 지킬 규칙

- **센터 대기열 (사용자 결정 11-17).** 전날 센터 발주서는 다음 날 아침 한 번 전용 업로드로 모으고 한국시간 발주처별 첫 제조사 작업에만 자동 합친다. 센터는 별도 Firebase 경로에서 트랜잭션 예약하며 검토 제외·보류·실패·삭제는 작업 행을 제거하고 대기열로 돌린다. 실제 제출 완료만 완료로 표시하고 `UNKNOWN`·제출 이력은 예약을 유지한다. 시간표 미정 업체는 표시만 하며 마감 30분 전 알림의 센터 단독 작업은 사람이 만든다. 기존 수취인·메모·승인·원장·잠금·금액 규칙을 유지한다. 상세는 `docs/center-order-queue.md`를 따른다.

- **애매하면 먼저 묻기 (사용자 지시 11-11).** 실제 주문·발송·데이터 변경처럼 되돌리기 어려운 작업에서 입력이나 대상이 애매하면 멋대로 고르지 말고 진행 전에 사용자에게 묻는다.
  - 예: 발주서 시트가 여러 개, 같은 업체 파일이 여러 개(수정본·추가본), 열 구성이 평소와 다름, 규칙에 없는 경우.
  - 발주서에 **보이는 시트가 2개 이상이면** 운영 화면에서 사람이 한 개를 선택할 때까지 보류한다(11-12). 시트 이름·사용 행 수·머리글과 숨김 시트 존재를 표시하며 숨김 시트는 후보에서 뺀다. 선택 이름·파일 시트 목록·행 출처가 맞지 않거나 정보가 없는 기존 작업은 워커가 HOLD한다. 보이는 시트가 한 개면 그 시트를 자동 선택한다.
  - 같은 원본 날짜·같은 업체 파일의 수정본·추가본 가능성은 화면에 경고한다. 이번 지시 범위에서는 이 경고만으로 자동 차단하지 않는다(11-12).
- **실제 발주 금지 (사용자 지시 11-05).** 지금은 학습과 준비 단계다.
  - 주문 제출, 결제, 메일·팩스·카톡 발송, 작업의 `SUBMIT_QUEUED` 전환, 주문 워커 실행을 하지 않는다.
  - 11-06 부분 허용: 보필몰과 이로움의 로그인, 장바구니 담기, 주문서 화면 열기, 주문서에 시험값 입력까지만 된다. 최종 제출은 금지다.
  - 장바구니 결과는 보고만 믿지 말고 장바구니 페이지를 직접 열어 대조한다.
- **신규 주소만 사용 (11-06).** 이로움은 `신규 배송지`, 보필은 `직접 입력`이다. 기본·최근 배송지, 배송지 목록, 수급자 목록은 쓰지 않는다.
- **메모에는 `비고(내역)`만.** 사이트의 '남기실 말씀'과 배송 메모에 주문번호나 설명을 덧붙이지 않는다. 비고가 비면 메모도 비운다.
- **원주문번호 공란 허용 (사용자 추가 지시 11-11).** 보필·이로움 모두 공란 또는 `THK`라는 이유로 보류하지 않는다. 원본 파일 계열·날짜·행·배송지·상품·수량으로 중복을 막는다. 실제 발주 금지와 승인·원장·잠금 조건은 그대로다.
- **납품처 수취인 확정 (사용자 추가 지시 11-16).** 마지막 구분자 뒤 기관·법인·영문·복수 이름·한 글자·가림 표기를 허용하며 끝 님·한글 뒤 D/H·앞뒤 복사 흔적만 제거하고 원문·정규화 기록을 보존한다. 빈 꼬리·주소 조각·확인된 사이트 길이 초과는 HOLD하며 구분자가 없는 미확정 경계는 추측하지 않는다. 보필 수취인 칸은 20자, 이로움은 확인된 제한이 없다. 상세 규칙 1~7과 새 유형은 `docs/b2b-http-ordering.md`를 따른다.
- **센터·지사 수취인 보완 (사용자 추가 지시 11-16).** 수취인이 비면 비고의 센터·지사 단어 우선, 없으면 파일명에서 찾는다. 선택한 출처의 후보가 없거나 복수이면 HOLD하며 보필 20자 제한을 적용한다. 기존 이름·기관명은 보존하고 출처와 실제 수취인을 표시한다. 일반 고객 빈 수취인은 계속 HOLD한다.
- **발주처 미정 부품 분리 (사용자 추가 지시 11-16).** 상품 연결표·발주처 학습에서 업체가 없거나 모호한 행은 `부품 주문(발주처 미정)` 별도 작업으로 분리하고 `HOLD`로 저장하며 자동 준비·제출에서 제외한다. 본체 모델이나 파일명으로 부품 발주처를 추정하지 않는다. 이번에는 지정된 부산센터 부품 3행의 보류 작업 한 건 생성만 허용했으며 기존 Firebase 작업은 변경·삭제하지 않는다.
- **보필 우편번호 확정 (사용자 추가 지시 11-12).** 지번은 시·군·구와 동·리·산 여부·본번·부번, 도로명은 시·군·구·도로명·건물 본번·부번이 일치하는 검색 결과가 한 개일 때만 사용한다. 전체 검색 결과가 여러 개여도 정확한 후보가 한 개면 가능하다. 시·도 차이는 고정 별칭표만 허용하며 표에 없는 차이·후보 복수·응답 미확인은 HOLD하고 운영 화면에 사유를 표시한다. 모의 자료 검증만 완료했으며 실제 고객 주소 보완이나 사이트 요청은 하지 않았다.
- **업체 분류와 표기는 직배 시간표가 기준 (11-05).** 시간표는 `worker/order-runner/data/direct-delivery-schedule.json`에 있다. 보필 발주마감은 사이트 표기와 달라도 시간표의 09:00이 기준이다.
- **온라인(서버) 방식이 기본이고, 화면 조작은 최후의 방법이다.**
- 아마란스와 IMS에서는 지시가 없으면 조회와 내려받기만 한다. 저장, 수정, 승인, 상태 변경은 하지 않는다.
- 비밀값과 로그인 정보는 GitHub Secrets나 로컬 메모에만 둔다. 원본 주문 파일과 분석 결과는 `.local-analysis/`에만 둔다.
