# 직배주문 공유 작업 기록

이 프로젝트는 Orca 작업 공간 여러 개와 Claude, Codex가 함께 작업한다. 대화끼리는 서로 보지 못하므로
**이 파일이 공유 인수인계 문서**다. 작업 절차는 `AGENTS.md`의 "Shared workflow"를 따른다.

이 저장소는 공개 상태다. 비밀번호, 승인 코드, 세션, 수취인 정보, 거래처 연락처, 내부 시스템 주소는 적지 않는다.

## 최종 목표

**멤버십 직배 주문의 자동화.** 업체별 주문 수단으로 발주를 자동 처리하고, 사용자 PC가 꺼져 있어도 돌아가야 한다.

```text
주문 취합(아마란스, 현재는 사람) → 업체별 분류·마감 확인 → 운영 페이지 검토·승인
→ 업체별 실행(B2B몰/ERP/메일/팩스/카톡) → 주문번호·결과 기록 → 입출고 등록(마지막 단계)
```

주문 데이터는 **IMS 개발이 끝날 때까지 아마란스에서 가져온다(11-09 사용자 확정).** IMS가 준비되면 출처를 IMS로 바꾼다.

## 작업 공간 = 세부 작업

각 Orca 작업 공간은 위 목표를 이루기 위한 **세부 작업 하나**다. 공간의 결과물은 모두 `main`에 모여
하나의 자동화 흐름으로 이어진다. 작업할 때는 내 공간의 결과가 앞뒤 단계와 맞물리는지 확인한다.

| 공간 | 브랜치 | 맡은 단계 | 진행 상황 |
|---|---|---|---|
| main | `main` | 전체 통합. 운영 페이지, 주문 워커, 이 문서 | 공유 규칙과 이 문서 정리(11-09) |
| 발주 시간표 및 스케줄 | `rlawltn260116-byte/learn-timetable-schedule` | 업체별 마감·발주 수단, 발주 준비, 사이트 주문 절차 학습 | 11-06까지 `main`에 반영함. `docs/direct-order-learning.md`, `tools/analyze_direct_orders.py`와 시험 파일은 커밋 전 |
| 입출고 등록 | `rlawltn260116-byte/입출고-등록` | 주문 완료 후 입출고 등록. 전체 흐름의 마지막 단계 | 운영 페이지에 명세서 검수→입고·출고→재조회 절차와 보류 기준 반영. 검수 결과 연동·실제 등록 절차 확인 대기 |

새 세부 작업을 시작하면 공간을 만들고 이 표에 맡은 단계와 함께 한 줄을 추가한다.

## 반드시 지킬 규칙

- **실제 발주 금지 (사용자 지시 11-05).** 지금은 학습과 준비 단계다.
  - 주문 제출, 결제, 메일·팩스·카톡 발송, 작업의 `SUBMIT_QUEUED` 전환, 주문 워커 실행을 하지 않는다.
  - 11-06 부분 허용: 보필몰과 이로움의 로그인, 장바구니 담기, 주문서 화면 열기, 주문서에 시험값 입력까지만 된다. 최종 제출은 금지다.
  - 장바구니 결과는 보고만 믿지 말고 장바구니 페이지를 직접 열어 대조한다.
- **신규 주소만 사용 (11-06).** 이로움은 `신규 배송지`, 보필은 `직접 입력`이다. 기본·최근 배송지, 배송지 목록, 수급자 목록은 쓰지 않는다.
- **메모에는 `비고(내역)`만.** 사이트의 '남기실 말씀'과 배송 메모에 주문번호나 설명을 덧붙이지 않는다. 비고가 비면 메모도 비운다.
- **업체 분류와 표기는 직배 시간표가 기준 (11-05).** 시간표는 `worker/order-runner/data/direct-delivery-schedule.json`에 있다. 보필 발주마감은 사이트 표기와 달라도 시간표의 09:00이 기준이다.
- **온라인(서버) 방식이 기본이고, 화면 조작은 최후의 방법이다.**
- 아마란스와 IMS에서는 지시가 없으면 조회와 내려받기만 한다. 저장, 수정, 승인, 상태 변경은 하지 않는다.
- 비밀값과 로그인 정보는 GitHub Secrets나 로컬 메모에만 둔다. 원본 주문 파일과 분석 결과는 `.local-analysis/`에만 둔다.

## 결정 기록

- 09-29: 운영 페이지는 GitHub Pages + Firebase + GitHub Actions 구조로 간다.
- 10-02: `.exe` 설치 방식 대신 완전 웹 방식으로 간다.
- 11-02: 주문 데이터 출처를 IMS로 정했다. 요청 행만 주문하고, 성공 행만 `진행중처리`하며, 행 식별값으로 중복을 막는다. 이 규칙은 IMS로 전환할 때 적용한다.
- 11-03: 카톡은 전용 PC와 발주 전용 카톡 계정으로 기존 방에 보낸다. 승인 없는 무인 실행이 필요하다.
- 11-06: 아마란스 수집 기준을 정했다(소분류=업체명이면 직배, 최근 30일, 주문수량≠미납수량이면 제외, 처리한 주문번호 제외, 수취인은 비고 우선). 자세한 내용은 `docs/amaranth-order-learning.md`.
- 11-06: 아마란스 취합 자동화는 보류하고, 사람이 만든 엑셀 이후 단계부터 자동화한다.
- 11-09: IMS 개발이 끝날 때까지 주문 데이터는 아마란스에서 가져온다. 입출고 등록은 전체 흐름의 마지막 단계다.

## 미결 사항

1. 카톡 발송을 전용 발송 프로그램으로 만들지. Claude의 11-03 제안에 아직 답이 없다.
2. 저장소 비공개 전환 방식(Cloudflare Pages 이전, GitHub Pro, 공개 유지).
3. 회사 Microsoft 365 Outlook 공용 사서함임은 확인했다. 커넥터 관리자 승인과 팩스 서비스는 미확인이다.
4. ERP(이카운트 등)에서 작성하는 문서 종류와 대상 업체.
5. 그레이스케일 발주 마감 시각.
6. 발주 시간표 공간의 커밋 전 파일을 올릴지.
7. 입출고 등록: 검수 결과·전표 이력 연동, 대표 명세서 대조, 실제 등록 메뉴·필수값·입력 순서·재조회 방법, 공식 API·엑셀 업로드 지원 여부 확인. 확정: 이메일 명세서는 Outlook ‘공급망혁신팀 공용’ 메일함, 명세서↔기존 주문 연결은 발주서의 수신자·주소·품목·수량 비교, 업체별 명세서 수신 경로(시간표 JSON), 명세서 한 건을 가상 입고·출고 한 쌍으로 처리, 수량 일치, 금액은 입고만 입력, 출고는 기존 주문을 출고 처리(출고처는 주문 기준, 금액은 품목 판매가 자동). 절차 화면은 반영했으며 실제 등록은 미연동이다. 설계는 docs/amaranth-statement-automation.md 참조.
8. 명세서 검수: 실제 발주서의 네 값 대조, 업체별 표본 확대·고유 문서/버전/중복 발송의 확정 집계, 진산메디칼 상세 뷰어 원본과 나이스텍·건강홈케어·코리아케어서프라이의 개별 거래명세서 대표 확보, 단위·세금·운임·부분 출고 처리 기준 확인. 상세 예외와 표본 빈도는 `docs/outlook-statement-audit.md` 참조.
