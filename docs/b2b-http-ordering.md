### 우편번호 규칙 변경 (사용자 승인, 이번 시험 한정 적용)

발주서에 우편번호 열이 없다. 기존 규칙은 "주소 검색으로 추측하지 않는다"였다. 이번에는 사용자 승인을 받아 다음 방식을 썼다. 보필 사이트 자체 우편번호 검색(`/share/postcode_search.php`의 `postcode_search_ps.php`, `keyword` POST)을 주문당 1회 조회한다. 결과가 정확히 1건이고 시·구·도로명·건물번호가 발주서 주소와 일치할 때만 결과의 우편번호와 도로명 주소를 기본주소로 쓴다. 기본주소 뒤에 남는 부분은 상세주소다. 0건, 2건 이상, 불일치는 HOLD다. 두 대상 모두 1건이 나왔고 일치했다. 주소 선택 브리지(`postcode_bridge.php`)는 구 우편번호 칸 `receiverZipcode`에 `-`를 넣는다. 그래서 이 값을 그대로 쓰도록 `http_queue.py`가 `legacyZipcode`(빈 값 또는 `-`만)를 받게 했다. 검색어와 결과 주소는 `.local-analysis/`에만 있다.

### 실행 순서와 확인

1. 로그인 → 빈 장바구니 → 주문내역 첫 페이지 식별자 기록.
2. 주문마다: BFSH10 담기 → 장바구니 단일 행·상품·옵션·수량 대조 → 주문서 `직접 입력`(신규 주소) → 서버 금액·배송비·신규 주소 지역 배송비·화면 합계·무통장 입금·필수 동의 구조·`reflectApplyDelivery` 미선택 검증(`submission_ready=true`) → 로컬 원장 예약 → `submit_prepared` 한 번 → 완료 페이지와 주문내역으로 대조 → 빈 장바구니.
3. 두 번째 주문은 첫 주문의 번호가 주문내역에서 확인된 뒤 3초 이상 지나 진행했다. 요청사항은 발주서 비고가 비어 있어 빈 값이었다.

### 첫 시도 중단과 수정

첫 시도에서 모든 검증을 통과한 뒤 `submit_prepared`가 요청 본문을 만들다 `TypeError`로 멈췄다. 원인은 보필 금액 렌더러가 돌려준 JSON `[이름, 값]` 목록을 `urlencode`가 받지 못한 것이다. 이 줄은 전송 호출보다 앞이었다. 그래도 제출 시도 표지가 켜졌으므로 UNKNOWN으로 멈췄다. 지휘자 승인으로 재로그인 1회를 했다. 주문내역 첫 페이지에 새 번호가 없음을 먼저 확인하고, 원장의 첫 항목을 지우지 않고 `NOT_SENT_VERIFIED`로 바꿨다. 남은 BFSH10 1행만 삭제하고 처음부터 다시 진행했다.

코드 수정:
- `http_amounts.py`: `verify_bofeel`이 렌더 결과를 `(이름, 값)` 쌍으로 되돌린다.
- `http_submission.py`: `validate_request`가 쌍 형식이 틀리면 제출 표지 전에 HOLD한다. 보필은 숨은 iframe 제출 응답이 `order_end.php?orderNo=` 이동 스크립트이므로 `bofeel_end_redirect`가 경고창 없는 같은 사이트 이동 1개만 읽어 `REDIRECTED`로 돌려준다. 이 상태는 접수 확정이 아니다. 실행기가 완료 페이지와 주문내역으로 대조한 뒤에만 성공으로 기록한다. 큐 경로(`submitOnePrepared`)는 `SUBMITTED`만 성공으로 보므로 `REDIRECTED`는 계속 UNKNOWN 처리된다.
- `http_queue.py`: 위 `legacyZipcode`.
- 시험 3건 추가. HTTP 시험 71건 통과.

남은 일: 주문서·완료 응답 원문 구조를 반영해 큐 경로의 완료 판정을 바꿀지, 상품 연결표·옵션·다품목 지원, 우편번호 규칙을 운영 규칙으로 둘지는 별도로 결정해야 한다. 제출 POST 자체는 세션 요청 기록(trace)에 남지 않는다. 그래서 전송 여부는 원장·완료 페이지·주문내역으로 판정했다.

`http_amounts.py`가 서버 조회·독립 산술·화면 결과를 대조한다. `amount_renderer.mjs`는 확인한 계산 함수만 해시로 고정하고 네트워크·파일·프로세스 접근이 없는 별도 VM에서 실행한다. 이로움은 계산 소스 전체, 보필은 주문별 숫자 리터럴만 정규화한 계산 구조를 검사한다. 페이지 초기화·주문 검증·제출 함수는 실행하지 않는다. 이 대조는 HTTP 기반의 격리 계산이며 실제 브라우저 화면 시험이나 최종 제출 응답 검증을 의미하지 않는다.

새 주소·원본 비고·상품·옵션·수량·서버 합계·화면 합계·결제·동의 중 하나라도 다르면 HOLD다. 검증한 필드 전체와 시각을 메모리 증명에 묶어 최종 함수 직전 다시 대조하며, 5분 경과·필드 변조·동의 상태 누락은 가짜 전송기 호출 전에도 차단한다. 예상 단가가 승인 행에 있으면 함께 대조한다. 실행당 단일 행·승인 증명·원장·행 잠금과 제출 환경 잠금은 유지한다. `submission_ready=true`는 금액 초안 대조 결과이며 실제 주문 허용을 뜻하지 않는다.

읽기 전용 상품 조회는 이로움 3회(DYJ-03 2회·DA-006 1회), 보필 3회(BFSH10 2회·BFMB20 1회)이며 같은 사이트 요청 사이 1초 이상이었다. DA-006 회색의 `io_id`와 사용·품절 표지, BFMB20 파스텔블루의 옵션 선택값에서 `optionSno`를 확인해 연결표에 추가했다. 두 옵션은 주문서 준비·금액 검증이 아직 미지원이므로 실행 시 HOLD다. 옵션 상품은 담지 않았다.

남은 제한은 다품목·복수 승인 행·옵션 상품 준비, 활성 묶음 할인·쿠폰·포인트·추가상품·해외배송·방문수령과 추가 배송비 비영 조합이다. 보필 `order_ps.php + set_recalculation`은 주문 처리 주소이므로 요청하지 않았으며 허용 목록에도 없다. 주문내역 불변 확인은 첫 페이지 범위다. 신규 우편번호는 승인 입력값을 요구하며 주소 검색으로 추측하지 않는다. 독립 검토 결과와 전체 시험·빌드·비밀값 검사는 증거 파일에 기록한다.

독립 검토는 `claude-opus-5-5/high`가 13개 파일 해시를 확인하고 차단 지적 없이 통과했다. 권장 보완으로 렌더러 자식에 PATH·Windows 실행 기본값만 전달하고 메모리 상한과 VM 마이크로태스크 시간 제한을 적용했다. Python 자식 시간 초과는 HOLD로 바꾸며, 두 번의 렌더 결과에서 금액 외 필드가 그대로인지 확인한다. 이로움 쿠폰·할인 식별자와 상품 할인 값도 빈 값 또는 정확한 0만 허용한다. 스위치·승인·원장 중복·행 잠금·복수 주문·잘못된 제출 명령·검증 실패 시 장바구니 정리 시험을 보완했고 Windows 기본 인코딩에서도 HTTP 시험이 통과했다. 이 보완 뒤 실제 사이트 요청은 하지 않았으며 변경 해시와 재시험은 증거의 `post_review_amendments`에 별도로 남긴다.

| 잠금 제출 | `http_submission.py`에 양 사이트 최종 POST 함수와 주소·메서드·필드 허용 목록. `submitOnePrepared`에서 승인 증명→일회성 원장→행 잠금→한 번 전송→결과 기록 | **현재 모든 실제 초안은 `submission_ready=false`다.** 이로움 최종 금액·배송비 재계산, 보필 결제·필수 동의 및 금액 검증이 미완료이므로 제출 경로는 HOLD. 가짜 전송기의 성공은 이 미확인 부분을 입증하지 않는다 |

| 큐·운영 화면 | 이로움은 `B2B_ORDER_TRANSPORT=http`로 선택 가능, 기본은 Playwright. 보필은 같은 큐에서 HTTP 준비 경로 선택. 화면에서 업체·배송지 묶음·신규 입력·HOLD 사유 표시 | HTTP 준비는 별도로 `ENABLE_B2B_HTTP_CART=true`와 업체 secret이 있어야 한다. 현재 workflow에는 새 큐 선택·제출 활성화를 추가하지 않았다 |

### 준비 흐름과 제한

`b2b-orders.mjs`는 공통 여섯 열 또는 운영 화면의 구조화된 행을 받아 정확히 확인된 연결표와 배송지를 대조한다. 우편번호는 원본에서 추측하지 않고 보완 전 HOLD한다. 고객 주문은 기존 THKC 규칙의 `SO` 뒤 10자리 식별자만 허용한다. 메모는 `비고(내역)`에 해당하는 `memo`만 사용하고 주문번호를 덧붙이지 않는다. 이 원칙에 맞지 않았던 기존 Playwright의 주문번호 메모 대체도 제거했다.

`b2b-queue.mjs`는 행을 표준 입력 파이프로 `http_queue.py`에 전달한다. 해당 업체의 로그인 값과 필요한 일반 환경만 전달하며 Firebase·GitHub 토큰·승인 키는 자식에게 넘기지 않는다. 원문 폼과 쿠키는 Python 메모리에만 남고 stdout에는 행 번호·상품번호·묶음·판정만 반환한다. stderr와 원문 예외는 출력하지 않는다. 준비 실패 뒤 재로그인·재전송하지 않는다. 한 실행에서는 HTTP 작업 하나만 준비하여 업체당 로그인 한 번을 넘지 않게 한다.

이로움은 신규 배송지 표지와 읽기 전용 검색 객체를 대조해 `select_item`과 같은 기본 옵션 상품 필드를 만든다. 검색은 상품별 한 번, 최대 30회, 요청 간 1초 이상으로 제한한다. `ct_price[]`는 원문 렌더러의 단가를 유지하고 수량은 `ct_qty[]`로 따로 전달한다. 서로 다른 행의 비고는 각각 `prodMemo[]`에 유지하며 서로 다른 문구를 배송 메모에 합성하지 않는다. 장바구니는 시작과 종료에 비어 있음을 확인한다.

보필은 현재 식별자가 확인된 BFSH10 기본 옵션만 준비한다. 동일 배송지에서 동일 상품·동일 비고인 행은 수량을 합치며, 다른 상품·상이한 행별 비고·동적 옵션은 HOLD한다. 빈 장바구니 확인→담기→행·수량 대조→주문서 GET→직접 입력 초안→이번 실행의 행만 삭제→빈 상태 확인 순서다. 다음 배송지 준비는 빈 상태 확인 뒤에만 허용한다. 캡차·잠금·추가 인증 신호면 삭제를 포함한 추가 요청도 멈추고 사람이 장바구니를 확인해야 한다.

### 제출 보호 조건

- `ENABLE_B2B_HTTP_SUBMIT`는 정확히 `true`여야 하며 기본 꺼짐이다. workflow에는 주입하지 않는다. 이 변수 하나로 현재의 금액·결제 HOLD를 해제할 수 없다.
- 선점 전 상태 `SUBMIT_QUEUED`, 운영 화면에서 `REVIEWED` 상태로 주문 확정한 기록, 검토 수락, 30분 이내이면서 미래가 아닌 최종 승인 시각, 기존 `FINAL_SUBMISSION_APPROVAL_KEY` 기반 증명이 모두 필요하다. 운영 화면과 서버가 `order-approval.mjs`로 같은 행 내용을 직렬화하고 상품·수량·배송지·메모까지 묶은 별도 `contentApprovalProof`도 검증한다. 승인 뒤 행을 바꾸면 HTTP·Playwright 모두 차단하며, 이전 형식의 승인도 새 준비·검토·확정을 거쳐야 한다. 현재 HTTP 초안은 `canSubmit=false`여서 운영 화면에 확정 버튼을 표시하지 않는다.
- 한 실행에서 제출 작업 하나, 한 주문·한 행만 허용한다. 준비와 제출은 같은 메모리 세션의 대조된 필드여야 하며 최종 전송 직전에 정확한 HTTPS 주소·POST·필드 허용 목록·신규 배송지·결제 분기를 재검사한다. 배송지 저장 필드는 허용하지 않는다.
- 기존 `.github/order-submission-ledger.json`에 승인 요청번호와 `b2b-row:<HMAC-SHA-256>` 키를 한 변경으로 예약한 다음 Firebase의 행별 `SUBMITTING` 잠금을 잡는다. 두 전송 경로가 공유하는 원본 주문번호·확정 모델·옵션 식별자를 별도 고정 비밀 `B2B_SUBMISSION_LEDGER_KEY`로 HMAC 처리한다. 공개 원장에는 원본 식별자의 단순 해시를 쓰지 않으며 고객정보도 넣지 않는다. 키는 32자 이상이어야 하고 없으면 전송 전 HOLD한다. 이 키는 승인 코드와 분리해 고정 보관하며 교체 전에 기존 중복 방지 기록을 이전하는 별도 절차가 필요하다. 다른 큐 작업·다른 승인으로 바꿔도 같은 키가 되고, Playwright와 HTTP 사이의 중복도 막는다. 원장을 오래됐다는 이유로 잘라내지 않으며 잘못된 원장 형식·GitHub 충돌·저장 실패는 전송 전 차단한다. 실제 원장과 Firebase를 이번 작업에서 변경한 것은 아니다.
- 전송 후 리다이렉트는 따라가지 않는다. 완료 문구와 번호가 하나로 확정되지 않거나 결과 저장이 실패하면 UNKNOWN으로 멈춘다. UNKNOWN 저장도 불가능하면 앞서 저장한 SUBMITTING 잠금이 남아 재시도를 막는다. 주문내역의 최신 번호를 이번 주문이라고 추측하지 않는다.
- PREPARE는 제출 플래그를 자식 프로세스에 전달하지 않고 승인 명령도 기다리지 않는다. SUBMIT에서는 보필 장바구니 행을 부모 승인 결정까지 유지하고, 전송한 뒤에는 추가 삭제 요청을 하지 않는다. 승인하지 않은 보관 행만 한 번 정리한다. 실행 한도 때문에 이번에 처리하지 않는 나머지 큐 작업은 선점 전 건너뛰어 기존 대기 상태로 남긴다.

검증과 독립 검토의 최종 판정은 Git 제외 경로 `.orca-routing/tasks/b2b-all/evidence.json`에 기록한다. 남은 작업은 옵션 식별자 확대, 두 사이트의 최종 금액·배송비·결제/동의 분기 확인과 그 모의 시험 보완, 실제 응답 구조의 추가 읽기 전용 대조다. 실제 발주와 workflow 실행은 계속 금지다.

최종 검증은 HTTP Python 모의 시험 51건·기존 도구 Python 시험 33건·Node 시험 37건(총 121건), 워커 빌드·화면 빌드·양쪽 TypeScript 검사·변경 파일 비밀값 검사·`git diff --check`를 통과했다. 독립 검토자는 잠금 상태의 준비·파서·연결부 안전성을 `passed=true`로 판정했고, 실제 제출 기능 완성이나 활성화 승인은 아니라고 명시했다. 최종 금액·결제 검증이 남아 있으므로 전체 요청은 부분 구현으로 보고하며 제출 항목은 HOLD다.

## Claude 이어받기: io_price 처리 확정, 보필 2단계 결과 확인, 기본 꺼짐 운영 연결 (2026-11-10)

Codex 한도로 Claude가 이어받았다. 이번 이어받기에서 **사이트 요청과 로그인은 0건**이다. 이어받기 전에 Codex가 오프라인 렌더 대조와 보필 2단계 실행을 이미 마친 기록(Git 제외 경로의 결과 JSON, 시작 표지 파일)을 확인했다. 그래서 보필을 다시 실행하지 않고 그 결과를 검증했다. 다시 실행하면 사이트당 1회 로그인 조건과 요청 반복 금지에 어긋난다.

### 1. 이로움 `io_price` 누락 처리 (오프라인)

저장된 주문서의 `select_item(obj, io_id, ct_qty)`는 jQuery `.val()`이 아니라 **문자열 연결로** 숨은 칸을 만든다(`'<input ... name="io_price[]" value="' + obj.io_price + '">'`). 그래서 검색 응답에 `io_price`가 없으면 브라우저도 문자 그대로 `undefined`를 넣는다. 함수 첫머리는 `io_type`이 없을 때 `'0'`을 넣는다. 옵션 없는 기본 상품(`options` 빈 배열)은 빈 `io_id[]` 숨은 칸을 만들고 `ct_price = parseInt(it_price)`로 계산한다. `io_price`는 `io_type === '1'`(추가 옵션) 분기에서만 가격 계산에 쓰인다. 따라서 파서는 `io_price[]=undefined`를 그대로 보존한다. 0이나 빈 값으로 고쳐 넣지 않는다. 검색 응답 키 구조에서도 `io_price`·`io_type`이 없고 `options`가 빈 배열임을 확인했다.

파서를 한 군데 좁혔다. `it_price`가 부호 없는 정수 문자열이 아니면 JS `parseInt` 결과를 추측하지 않고 멈춘다. `ct_price[]`는 `parseInt`와 같은 정수 문자열이다. 모의 시험에 `io_type` 기본값, 앞자리 0, 쉼표·소수·불리언 단가, 필수 속성 누락 거부를 추가했다.

오프라인 대조 결과는 다음과 같다. 저장된 `select_item`과 `get_delivery_ca_id`만 떼어 Node `vm` 격리 환경에서 jQuery 대역으로 실행했다. 저장된 검색 응답 객체를 넣어 얻은 동적 상품 칸 24개를 직렬화했고, 그 결과가 파서 출력과 이름·순서·값까지 같았다. 상품 목록 `ul#so_item_list`는 `form#simple_order` 안에 있어 렌더된 칸이 제출 폼에 포함되는 구조다. 저장된 주문서 기본값과 이 상품 칸, 시험 수취인값(수취인·연락처·주소·상세주소·요청사항, 시험 우편번호)으로 메모리 초안을 만들어 폼 필드와 대조했다. 판정은 다음과 같다.

| 항목 | 판정 |
| --- | --- |
| 누락 필드 | 0개 (`it_id[]`, `io_id[]`, `ct_qty[]`, `prodMemo[]` 포함) |
| 신규 배송지 표지 `data-value=new` | 확인 |
| 바꾼 필드 | `od_b_name`, `od_b_tel`, `od_b_hp`, `od_b_zip`, `od_b_addr1`, `od_b_addr2`, `od_memo` 7개 |
| 그 밖의 기본값(결제·쿠폰·증빙·숨은 값) | 변경 없음 |
| 폼 action | `orderformupdate.php`와 일치. **전송하지 않음** |
| 제출 허용 | `false`. 합계·배송비 재계산은 검증하지 않음 |

한계: jQuery 대역은 실제 jQuery가 아니다. `ct_qty[]`는 `it_buy_inc_qty`로 다시 설정되는데, 파서가 증가 수량 1만 허용하므로 같은 결과다. 우편번호는 시험값이며 주소 검색으로 검증하지 않았다. 초안의 상품 칸은 폼 끝에 붙인다. 상품 배열끼리의 순서는 실제와 같지만 다른 필드와의 상대 위치는 실제 DOM과 다르다. 서버가 `io_price[]=undefined`를 어떻게 처리하는지는 제출하지 않았으므로 확인하지 못했다.

### 2. 보필 2단계 (Codex 실행분 검증)

Codex 실행 기록은 다음 순서다. 시작 표지 파일을 만든 뒤 1회만 실행하는 스크립트로 로그인 GET 200 → 로그인 POST 200(이동 HTML) → 장바구니 GET 200(빈 상태 확인) → 상품 GET → BFSH10 기본 옵션 1개 담기 POST(`mode=cartIn`) → 장바구니 GET(단일 행 대조) → `order.php` GET → 장바구니 GET(같은 행 재확인) → 해당 `cartSno[]`만 삭제 POST(`mode=cartDelete`) → 장바구니 GET(빈 상태)를 수행했다. 로그인 POST 1회, 재시도 0회, 변경 예약은 담기·삭제 각 1회다.

'전체 상품 주문'은 현재 장바구니 HTML의 `gd_order_all()` 함수가 저장된 함수와 공백을 빼고 같고 쿠폰 적용 표지가 없을 때만 `order.php` GET으로 대신했다. 쿠폰이 있으면 `cart_ps.php` 검사 POST가 끼므로 이 경우는 멈춘다. 주문서 초안은 `직접 입력`(`shipping=shippingNew`, 라벨 대조) 표지를 확인했다. 수취인·우편번호·주소·상세주소·전화 2개·`orderMemo`와 `shipping`만 바꿨고 누락 필드 0개, `cartSno[]`가 담은 행과 일치, action `order_ps.php` 일치(전송 안 함), 기본값 보존, 제출 허용 `false`였다. `reflectApplyDelivery`(회원 배송지 반영)와 `csrfToken`·결제 필드는 바꾸지 않았다. `order.php` GET이 서버 임시 상태를 만드는지는 여전히 확인하지 못했다.

### 3. 운영 연결 (기본 꺼짐)

## 추가 소스 판정: 상품 조회 전용 여부와 응답 구조 확인 대기 (2026-11-10)

이어서 저장된 주문서의 `select_items`, `select_item`, 상품 검색 이벤트를 읽었다. `ajax.get_item.php`는 상품 자동완성 검색 URL이면서 선택 후 `it_id`만 POST해 `is_buy`·`soldout_ck`를 검사하는 URL이다. 주문서·수취인·장바구니 행 식별값을 보내지 않고, 상품 행 추가는 성공 콜백 이후 클라이언트의 `select_item`이 수행한다. 따라서 클라이언트에서 관찰한 용도는 상품 검색과 구매 가능 여부 확인이다. 다만 저장 자료는 HTML/JavaScript이며 서버 PHP 구현이나 해당 응답 표본은 없으므로, 서버에서 장바구니·주문 상태를 변경하지 않는다는 점은 아직 확인하지 못했다. 지휘자가 정한 “불확실하면 보내지 말고 질문” 조건에 따라 로그인과 해당 POST를 보내지 않고 확인을 요청했다.

또한 `select_items`의 콜백은 응답 `data`를 `select_item`에 전달하지 않고 기존 인수 `obj`와 `items`를 사용한다. 자동완성 선택 콜백도 검색에서 받은 `obj`를 유지하고 POST 응답에서는 두 제한 플래그만 읽는다. `select_item`은 네 가지 핵심 필드 외에 가격·최소/최대/증가 수량·배송비·카테고리·재고 상태 등 여러 필드를 `obj`에서 만든다. 따라서 **`it_id` POST 응답만으로 전체 상품 객체를 얻을 수 있다는 가정은 소스로 확인되지 않는다.** 조회 응답에 그 객체가 포함되는지 확인하거나 별도 상품 검색 요청의 범위를 확정해야 하며, 누락 가격·옵션·배송 필드를 임의로 만들지 않는다.

이번 이어받기에서는 사이트 요청·로그인 정보 열람·장바구니 변경을 하지 않았고, 보필 2단계와 운영 연결은 앞 단계 확인 전이라 시작하지 않았다. 기존 변경은 유지했으며 커밋·푸시·워크플로 실행은 하지 않았다. `origin/main`이 현재 HEAD의 조상인 것을 확인해 추가 병합은 필요하지 않았다.

## 추가 확인: 주문서 이동 성공, 상품 필드 대조 미완료 (2026-11-10)

## 로그인과 세션

브라우저 기존 세션이 풀려 사이트별 폼 로그인 1회로 성공했다. 이후 Aside 앱이 중단되어 지휘자가 복구했고, 재시작에 따른 새 로그인 허용을 받아 다시 사이트별 1회로 성공했다. 최초 이로움 UI 조작은 제출 요소 종류를 잘못 지정해 요청 전에 중단됐고, 예약한 재시도 1회를 사용해 `input[type=submit]`으로 바로잡았다. HTTP 로그인 POST를 별도로 반복 시험하지 않았다.

추가로 브라우저 없는 Python HTTP 클라이언트가 빈 쿠키 저장소에서 각 로그인 페이지를 GET했다. 양쪽 모두 HTTP 200, HTTP 리다이렉트 없음이었으며 폼·스크립트·쿠키 이름을 읽었다. 이 GET은 실제 인증 성공 시험이 아니다.

### 이로움

- 시작: `GET https://eroumcare.com/bbs/login.php`.
- 폼: `name=flogin`, `method=POST`, action `/bbs/login_check.php`, `application/x-www-form-urlencoded`.
- 필드: `mb_id`, `mb_password`, 숨은 `url`; 선택 체크박스 `auto_login`. 체크하지 않은 체크박스는 보내지 않는다. `url`은 반환 경로이므로 같은 사이트의 승인된 경로로 제한한다.
- 읽은 `flogin_submit`은 ID·비밀번호 공백 검사 후 일반 폼 제출만 한다. 이 폼에서는 숨은 CSRF 토큰·암호화용 생성 토큰·캡차를 관찰하지 않았다. 추가 인증이 다른 조건에서도 없다는 보장은 아니다.
- 관찰한 로그인 페이지 응답 쿠키 이름: `PHPSESSID`, `2a0d2363701f23f8a75028924a3af643`. 값은 보존하거나 문서화하지 않는다. 어떤 쿠키가 인증에 반드시 필요한지는 제거 실험을 하지 않아 미확정이다. HTTP 클라이언트는 서버가 설정한 쿠키 전체를 도메인·경로·만료 조건대로 관리한다.
- 브라우저 로그인 후 최종 경로는 `/`였다. 인증 POST 응답의 정확한 HTTP 리다이렉트 상태 코드·중간 경로는 이번에 수집하지 못했다. 운영에서는 허용된 같은 사이트 경로만 따라가고, 응답 200 여부 대신 인증된 장바구니·계정 상태로 성공을 판정해야 한다.

### 보필

- 시작: `GET https://bofeelmall.com/member/login.php`.
- 폼: `id=formLogin`, POST. HTML action은 `https://www.bofeelmall.com/member/login_ps.php`지만, 실제 페이지의 submit 핸들러는 `$.post('../member/login_ps.php', params)`로 가로챈다. 운영에서는 관찰한 같은 origin의 `https://bofeelmall.com/member/login_ps.php`를 대상으로 설계하고 임의의 외부 호스트로 자격증명을 전달하지 않는다.
- 필드: `mode`, `returnUrl`, `secretKey`, `encryptFl`, `loginId`, `loginPwd`, 선택 `saveId`. 비회원 주문조회용 `formOrderLogin`은 별도 폼이며 사용하지 않는다.
- `secretKey`는 로그인 GET HTML에 값이 있는 숨은 필드다. 같은 쿠키 저장소로 페이지를 받은 뒤 해당 응답의 값을 사용한다. `encryptFl`은 관찰 시 `Y`였다. 키·쿠키·토큰 값은 로그에 남기지 않는다.
- **ID와 비밀번호 모두 브라우저 JavaScript에서 암호화한다.** 평문을 `loginId`·`loginPwd`에 그대로 보내는 HTTP 구현은 현재 폼과 다르다.
- 관찰한 암호화 구조: 각 문자열마다 새 IV 16바이트와 salt 256바이트를 생성한다. 숨은 `secretKey`를 키 재료로 PBKDF2-HMAC-SHA512, 반복 999회, 파생 키 32바이트를 얻는다. AES-256-CBC와 CryptoJS 기본 PKCS#7 패딩으로 암호화한다. 결과는 `{ciphertext, iv, salt, iterations}` JSON이며 ciphertext는 Base64, iv·salt는 hex이고 JSON의 UTF-8 바이트 전체를 다시 Base64로 감싼다. ID와 비밀번호는 각각 암호화하므로 난수도 각각 생성한다.
- 이 계산은 일반 암호 라이브러리로 브라우저 없이 재현할 수 있는 구조다. 이번에 운영용 암호 코드를 구현하거나 브라우저 없는 인증 POST를 실행하지 않았으므로 상호운용 성공은 아직 검증하지 않았다. 운영 전 실제 자격증명 없이 만든 고정 입력으로 CryptoJS와 HTTP 클라이언트 암호 결과를 대조해야 한다.
- 로그인 AJAX 콜백은 JSON의 `code`, `message`, `url`을 검사하고 성공 분기에서 `returnUrl` 또는 `/`로 JavaScript 이동한다. 오류 분기에서도 `url` 이동이 가능하므로 이동만으로 성공을 판정하면 안 된다. 브라우저 시험 최종 경로는 `/main/index.php`였다. 정확한 HTTP 응답·리다이렉트 체인은 수집하지 않았다.
- 로그인 GET에서 관찰한 쿠키 이름: `GD5SESSID`, `GMCS`, `analytics_client_id`, `analytics_session_id`, `analytics_session_date`, `analytics_session_channel`. 도메인은 `.bofeelmall.com`이었다. 처음 두 쿠키와 analytics 쿠키의 인증상 필수 여부는 분리 시험하지 않았다. 세션 쿠키와 서버 토큰의 유효기간·회전 규칙도 미확정이다.
- 관찰한 일반 로그인 폼에는 캡차가 없었다. `secretKey`는 서버가 제공하고 암호문·IV·salt는 클라이언트가 계산한다. 다른 접속 조건의 추가 인증·차단이 나오면 우회하거나 반복하지 않고 중단한다.

## 장바구니 HTTP 규약

모든 변경 시험은 로그인된 페이지에서 같은 origin의 `fetch`로 URL 인코딩 POST를 직접 전송했다. 버튼의 주문 함수를 호출하지 않았다. 브라우저 세션 쿠키는 자동 동반됐으며 쿠키 값은 출력하지 않았다. AJAX 담기는 `X-Requested-With: XMLHttpRequest`도 보냈다. 이 헤더가 필수인지 별도 제거 시험은 하지 않았다. 장바구니와 사후 주문내역의 판정은 Aside가 렌더링한 DOM을 읽었다. 브라우저 없는 원본 HTML 파서로 같은 판정이 가능한지는 운영 전 검증해야 한다.

### 이로움

BFSH10의 상품 번호는 `1000000025`다. 옵션 없는 기본 행·수량 1이었다. 핵심 상품 필드는 `goodsNo[]`, `optionSno[]`, `goodsCnt[]`다. 추가로 `mode`, `scmNo`, `cartMode`, `ac_id`, `useBundleGoods`, `deliveryCollectFl`, `deliveryMethodFl`, `goodsDeliveryFl`, `sameGoodsDeliveryFl`, `optionFl`, `brandCd`, `cateCd`, 세금·할인·마일리지·가격 계산 필드와 `couponApplyNo[]` 등이 직렬화됐다. 필드 이름과 값의 공급 위치만 기록하며 단가·계산 금액은 이 문서에 넣지 않는다.

폼에서 읽은 계산 필드·옵션 번호를 그대로 전달한 시험이므로 최소 필수 필드 집합은 아직 확정되지 않았다. `ac_id`를 CSRF 토큰으로 단정하지 않으며, 의미가 미확정인 숨은 값도 새 응답에서 읽어 보존한다. 서버가 최종 가격을 검증해야 한다는 가정과 별개로 클라이언트가 계산 값을 임의 변경하지 않는다.

삭제 직렬화 필드는 `mode`, `cart[cartSno]`, `cart[goodsNo]`, `cart[goodsCnt]`, `cart[addGoodsNo]`, `cart[addGoodsCnt]`, `cart[couponApplyNo]`, `useBundleGoods`, `ac_id`, `cartSno[]`였다. 기존 상품 삭제는 추가 승인에 따라 두 `cartSno[]`를 한 POST로 보냈다. 이후 시험 삭제에는 BFSH10 한 행만 포함했다. 응답 HTML의 스크립트를 HTTP 클라이언트에서 실행하지 않고 GET 조회로 검증한다.

소스의 `gd_cart_remove`는 `GET /order/cart_ps.php?mode=remove`를 iframe으로 보내 전체를 비운다. 이는 이름이 GET이어도 변경 요청이다. 이번에는 사용하지 않았고 운영 허용 목록에도 넣지 않는다. `cart_ps.php`는 mode에 따라 기능이 바뀌므로 경로만 허용해서는 안 된다. `cartMode=d`, `pa`, `mode=orderSelect` 및 주문 이동 분기는 차단한다.

## 주문서 제출 구조 — 읽기만 수행

두 사이트 모두 GET HTML을 DOM으로 읽거나 소스를 파싱했다. 폼 제출·검증 함수 호출·약관 선택·주소 입력·저장은 하지 않았다. 주문서 GET이 서버 임시 상태를 만들거나 바꾸는지는 확인하지 못했다. 페이지 스크립트 미실행과 주문내역 불변을 서버 상태 무변경의 증거로 해석하지 않는다. 주문서의 쿠키·토큰·개인정보가 포함될 수 있는 원문은 `.local-analysis/http-ordering/`에만 두고 저장소에 추가하지 않는다.

## worker/order-runner 운영 모듈 제안

현재 `worker/order-runner`의 Playwright 의존 구현과 별도로 다음 경계를 갖는 HTTP 어댑터를 제안한다. 이번에는 파일·패키지·운영 동작을 변경하지 않았다.

| 구성 | 역할 |
| --- | --- |
| `VendorHttpSession` | 사이트·계정별 독립 쿠키 저장소, TLS 검증, 타임아웃, 허용 호스트·경로·메서드·mode 검사 |
| `EroumCartClient` | 로그인 GET·폼 POST, 상품 폼 파싱, 담기·실제 행 조회·시험 행 삭제 |
| `BofeelCartClient` | 로그인 GET·서버 키 추출·암호화·로그인 AJAX, 상품 폼 파싱, mode 제한 담기·조회·삭제 |
| `CartOperationJournal` | 요청 전 의도·상품 식별자·수량·생성 행 식별자·결과 상태 기록, 민감 값 제외 |

1. Node HTTP 클라이언트와 검증된 쿠키 저장소를 사용한다. 기본 `fetch`만으로는 쿠키가 자동 보존되지 않으므로 `Set-Cookie`와 도메인·경로·Secure·만료를 처리하는 쿠키 저장소 연동이 필요하다. HTTP 클라이언트가 HTML 폼을 파싱하며 Aside·CDP·Playwright·브라우저 설치를 운영 전제로 삼지 않는다.
2. 계정 비밀값은 승인된 비밀 저장소에서 런타임에 읽는다. 인증 POST 본문, Cookie·Set-Cookie 헤더, 서버 키·CSRF 값, 금액·고객정보를 로그에서 제외한다. 쿠키 파일은 저장소 밖의 제한된 경로에 두고 운영체제 비밀 저장소에 연결한 암호화로 보호한다. 이는 설계 제안이며 이번에 PC 권한·저장소 설정은 바꾸지 않았다.
3. 로그인 페이지를 같은 쿠키 저장소로 GET하고 숨은 필드를 그 응답에서 읽는다. 보필은 앞서 설명한 암호화를 브라우저 없는 라이브러리로 재현한다. 인증 실패·캡차·새 인증 요구가 나오면 한 번에서 멈춘다. 로그인 성공은 인증된 페이지 구조로 검증한다. HTTP 200이나 이동 경로만으로 판정하지 않는다.
4. 사이트·계정별로 한 작업만 실행한다. 담기 전 장바구니를 읽고 예상 상태를 확인한다. 옵션은 상품 페이지의 실제 옵션 ID·표시명 대응으로 선택한다. 담기는 직렬화 배열의 중복 키 순서를 유지하며, 서버가 보낸 숨은 값을 임의로 줄이지 않는다.
5. 변경 요청의 자동 재전송을 끈다. 타임아웃·연결 종료·불명확한 응답이면 `uncertain`으로 기록하고 조회만 해서 결과를 확인한다. 확인되지 않은 담기·삭제를 다시 보내지 않는다. GET 이름만으로 안전성을 판단하지 않고 전체 삭제 GET 등 변경 경로도 거부한다.
6. 담기 후 행 단위 상품 ID·모델·옵션·수량·실제 행 식별자를 대조한다. 보필의 JSON 오류값은 숫자·문자열을 정규화해 판정하고, 성공 응답도 장바구니 재조회로 대조한다. 삭제는 해당 실행에서 생성한 행만 대상으로 한다. 이로움 `seldelete`가 옵션 행보다 상품 ID 단위로 삭제할 가능성은 미확정이므로, 담기 전 같은 `it_id`가 이미 있으면 중단한다. 삭제 직렬화 시 대상 외 `ct_chk`를 명시적으로 제거하고 상품 ID도 대조해야 한다. 기존 장바구니를 비우는 기능은 별도 명시적 승인 작업으로 분리하며 일반 시험·운영 실패 복구에서 자동 사용하지 않는다.
7. 허용 목록은 이로움 담기 `itemcart.php + sw_direct=0`, 삭제 `cartupdate.php + act=seldelete`, 보필 `cart_ps.php + mode=cartIn/cartDelete`처럼 payload 조건까지 검사한다. 로그인은 별도 어댑터에서만 허용한다. 주문·결제·회원정보·배송지 저장과 임의 URL 요청 기능은 이 모듈에 제공하지 않는다.
8. 쿠키 만료·세션 회전·HTML 구조 변경을 감지하면 진행을 중단한다. 로그에는 경로·메서드·상태 코드·필드 이름·승인된 상품 모델·수량·검증 결과만 남긴다. 원문 HTML·HAR을 운영 로그로 수집하지 않는다.

운영 도입 전 남은 검증은 브라우저 없는 양 사이트 로그인, 보필 암호화 상호운용, 세션 만료·회전·오류 응답, 각 사이트 수량·옵션 파서, 다중 옵션과 최소 필드 의존성이다. 이번 장바구니 시험 성공으로 실제 주문 제출이나 전체 운영 준비가 완료됐다고 판단하지 않는다.

## 증거와 독립 검토

민감 원문은 Git 제외 경로 `.local-analysis/http-ordering/`에 있다. 시험 결과 `eroum-test.raw`, `bofeel-test.raw`는 응답 본문·쿠키 값 없이 단계별 상태와 필드 이름을 기록한다. 로그인 구조 원문과 주문서 원문은 외부로 공유하지 않는다. 라우팅 완료 증거는 `.orca-routing/tasks/a3fe96568ff341a7/evidence.json`에 기록한다.

`claude-opus-5-5/high` 독립 읽기 전용 검토는 통과했다. 검토의 비차단 지적을 반영해 행 단위 ID·수량 추출의 한계, 조회의 브라우저 의존, 삭제 단위의 불확실성, 오류값 정규화, 주문서 GET의 임시 상태 가능성을 위에 명시했다. 암호화의 호출부는 작성자가 소스로 확인했으나 검토자는 별도로 확인하지 못했고, 실제 인증 상호운용도 미검증이다. 전체 검토 결과는 완료 증거의 `independent_review`와 별도 검토 JSON에 남긴다.

- 기존 HTTP 로그인·장바구니 시험 결과와 빈 상태 확인 기록은 유지했다. 이번 실행에서 실제 로그인 제출, 담기, 주문서 이동, 삭제 요청은 보내지 않았다.
