# 명세서 기반 아마란스 입출고 자동화 준비

2026-11-09 사용자 요청: 거래처가 메일·카톡·팩스로 보내는 명세서를 바탕으로 아마란스 입고·출고 등록을 자동화한다. 전체 직배 주문 흐름의 마지막 단계이며, 이 문서는 구현 전 설계안이다. 수신 연동, OCR, 아마란스 등록은 아직 구현하거나 검증하지 않았다.

## 제안 흐름

명세서 원본 보관 → 문서·품목 추출 → 거래처·품목 코드 대응 → 기존 주문과 대조 → 검토 후보 생성 → 승인된 방식으로 아마란스 등록 → 전표 재조회·대조 → 완료 기록.

첫 단계는 채널별 자동 수신보다 사람이 모은 파일을 입력하는 드라이런으로 시작한다. 대표 양식과 업무 규칙이 확인되면 수신 연동과 등록을 순서대로 연결한다. 현재 아마란스에서는 조회·내려받기만 수행하며, 저장·승인·전표 처리는 실행하지 않는다.

## 입력과 수신 경로

| 경로 | 초기 입력 | 자동 수신 전 확인할 내용 |
|---|---|---|
| 메일 | 첨부 PDF·엑셀·이미지와 필요한 본문 | 계정 종류, 읽기 권한, 대상 폴더, 첨부 없는 명세서 처리 |
| 카톡 | 사용자가 내려받은 첨부·이미지 | 실제 수신 계정·방, 제공되는 연동 방식, 전용 PC 의존성 |
| 팩스 | 수신 PDF·이미지 | 수신 서비스, 내려받기·메일 전달·공식 연동 지원 여부 |

어느 채널도 현재 자동 접근이 된다고 가정하지 않는다. 온라인 실행을 우선하며, 카톡 PC 화면 조작만 가능한 경우에는 사용자 PC가 꺼져도 돌아간다는 목표와 충돌하는지 먼저 확인한다. 외부 OCR 전송과 새 과금 서비스 연결은 이번 범위에 포함하지 않는다.

### 업체별 명세서 수신 경로 (2026-11-09 사용자 제공)

업체별 값은 `worker/order-runner/data/direct-delivery-schedule.json`의 `statementChannel`에 있다. 32개 발주 회차 기준으로 이메일 17, 카톡 8, 팩스 3, B2B몰 2, ERP 2다. 발주 수단과 명세서 수신 경로가 다른 업체가 있다(예: 카톡으로 발주하고 이메일로 명세서를 받는 업체). THK는 오전·오후 회차 모두 이메일이다(사용자 확인). 이메일이 가장 많으므로 첫 자동 수신 대상은 이메일로 둔다. 이메일 명세서는 회사 Microsoft 365 Outlook의 사용자 지정 공용 사서함으로 받는다(2026-11-09 확인). 커넥터는 관리자 승인 문제로 연결하지 못했다. 이후 사용자가 메일 열기와 읽음 상태 변경을 허용하여 로그인된 Aside 브라우저로 이메일 대상 14개 업체를 표본 조사했다. 본문 확인 검색 귀속은 업체별 합계 242개(업체 간 중복 제거 고유 236개)다. 무관 메일도 포함돼 업체별 실제 수신 건수나 고유 명세서 수로 쓰지 않는다. 실제 HTML·PDF·JPG의 양식과 정정·반품·부분 출고 등 예외, 미확인 범위는 [Outlook 명세서 양식·특이 사례 검수](outlook-statement-audit.md)에 기록했다. 업체별 수백 건 전수 검수와 전체 고유 명세서 건수 확정은 미완료다.

### 실제 표본에서 확인한 입력 분기

- 메일 → 조회 문서 → 조회 쪽 → 인쇄 쪽 → 품목 행을 구분한다. THK는 여러 조회 쪽에 전체 합계가 반복되고, 안앤락·명성실버케어에는 한 조회 화면 안에 인쇄 쪽별 소계가 있다. 제목의 `외 N건`이나 쪽 수를 문서 건수로 쓰지 않는다.
- 첨부 없는 이카운트·WEHAGO 링크, 텍스트 PDF, JPG를 별도 추출 경로로 둔다. WEHAGO 표 값은 input에 있어 본문 텍스트만으로 수집하면 빈 값이 된다. 이카운트의 3개월 열람 제한 안내에 대비해 수신 시점 원본 보관이 필요하다. 실제 수신·추출 기능은 아직 구현하지 않았다.
- 여러 납품처가 한 문서에 섞이고, 품명·적요에 수취인·바코드·발송일이 결합되거나 바코드별 여러 행으로 나뉜다. 베스타에는 수취인 없는 대량 납품 행도 있어 시간표 업체명만으로 모든 명세를 직배로 분류하지 않는다.
- 월간 집계, 기간별 거래보고서, 세금계산서, 송장 안내, 발주서·회신은 일별 납품 명세와 구분한다. 삼원스카이 기간 보고서에는 일별 반품 명세와 같은 거래가 있어 둘 다 신규 입출고로 등록하면 중복된다.
- 상품·양수 운임·음수 반품·과세 및 세액 공란 행을 분리하고, 쪽별 소계·총계·전잔금·미수잔액을 구분한다. 표시 단가와 수량의 곱이 원 단위로 다른 사례를 임의 보정하지 않는다. 작성일·거래일·발송일·수신일도 별도로 보관한다.
- 명성실버케어는 수취인·배송지 주소 열을 확인했지만 여러 다른 양식에는 회사 주소만 있다. 회사 주소를 배송지로 쓰지 않는다. 네 값 대조 규칙을 유지하며, 주소 누락·복수 주문·부분 납품·정정·음수·중복 후보는 보류한다. 삼원스카이 본문에서 6개 중 4개 선출고·2개 후속 출고 예정 사례를 확인했다.

## 추출할 후보 정보

문서별로 수신 경로, 원본 해시, 문서번호, 문서일자, 거래처 식별자, 공급가액·세액·합계, 정정 여부와 원문 위치를 유지한다. 품목별로 원문 품명·규격·단위·수량·단가·금액, 확인한 아마란스 품목코드, 연결한 주문번호와 행 식별값을 유지한다.

실제 등록에 필요한 사업장·창고·거래구분·과세구분·담당자·등록일자와 필수 열은 입출고 화면 또는 공식 업로드 양식을 읽어 확인한 뒤 확정한다. 주문미납현황의 내려받기 열을 등록 양식으로 재사용하지 않는다. 직배는 제조사가 고객에게 바로 출고하므로 우리 창고에 실물이 들어오지 않는다. 입고·출고 등록은 재무 처리를 위한 가상 입고→출고이며, 명세서 한 건을 입고 1건과 출고 1건의 한 쌍으로 처리한다(2026-11-09 사용자 확인). 따라서 창고 검수·재고 실사 단계는 두지 않는다. 입고와 출고는 날짜·품목·수량이 일치해야 한다. 금액은 입고 때만 명세서 금액을 입력하고, 출고 금액은 아마란스가 자동으로 채우므로 입력하지 않는다(대조만 한다). 출고 등록은 아마란스의 기존 주문을 출고 처리하는 것이다. 출고처는 그 주문에 이미 들어 있으므로 자동화가 따로 판단하지 않는다. 출고 금액은 품목에 등록된 판매가로 자동 입력된다(2026-11-09 사용자 확인).

## 검증과 보류 기준

- 문서가 여러 페이지면 페이지 누락·반복과 합계 행을 먼저 확인한다. OCR 결과에는 원본 위치를 연결하고, 읽지 못한 숫자는 추측하지 않는다.
- 거래처·품목은 확인한 코드 대응표로 연결한다. 이름 유사도만으로 코드를 확정하지 않으며 규격·단위·포장수량이 다르면 보류한다.
- 수량·단가·금액과 문서 합계를 대조한다. 소수점, 세금 포함 여부, 할인·운임·반올림은 업무 규칙이 확인되기 전 자동 보정하지 않는다.
- 명세서는 그 업체에 보낸 발주서와 수신자·주소·품목·수량을 비교해 기존 주문에 연결한다(2026-11-09 사용자 확인, 명세서에 우리 주문번호가 있다고 가정하지 않는다). 네 값이 모두 맞는 주문이 정확히 하나일 때만 자동 연결하고, 후보가 없거나 둘 이상이면 보류한다. 주소는 띄어쓰기·표기 차이를 정리한 뒤 비교하되, 다르면 추측하지 않는다.
- 연결한 주문의 행과 품목·수량을 대조한다. 부분 납품, 합배송, 하나의 문서에 여러 주문, 주문 없는 명세서는 별도 검토한다. 발주 준비 단계의 ‘부분 출고 주문 전체 제외’ 규칙을 입출고 단계에 그대로 적용하지 않는다.
- 반품·음수·취소·정정 명세서는 일반 입출고와 분리한다.
- 동일 파일은 해시로 찾고, 메일·팩스 등 다른 경로의 동일 문서는 거래처·문서번호·일자·명세 내용으로 중복 후보를 찾는다. 문서번호 없는 경우와 정정본은 사람이 판단한다.

## 등록 연결 조건

아마란스의 공식 API 또는 엑셀 업로드 지원 여부를 먼저 조회·확인한다. 현재 지원 여부와 대상 메뉴는 미확인이다. 화면 자동 입력은 다른 경로가 없을 때 검토한다.

등록 연결 전에는 검토 후보의 상태와 실제 전표 완료 상태를 분리한다. 입고·출고를 각각 기록하고 한쪽만 성공한 경우 성공한 전표를 재생성하지 않는다. 실행 이력은 영속 저장하고 동시 실행을 막는다. 저장 후 응답이 끊기면 재제출하지 않고 기존 전표를 조회해 대조하며, 전표번호와 품목·수량·금액 확인 전에는 완료로 표시하지 않는다. 실제 등록 방식과 재조회 식별자는 화면 학습 후 결정한다.

## 구현에 필요한 자료

1. 확보한 10개 업체 대표 양식과 원본 발주서의 실제 대조. 진산메디칼 상세 문서, 나이스텍·건강홈케어·코리아케어서프라이의 개별 거래명세서 대표는 추가 확보가 필요하다. 민감 자료와 원문 위치는 `.local-analysis/outlook-statement/`에만 보관한다.
2. 해당 명세서 한 건을 현재 입고·출고로 처리하는 순서: 대상 메뉴, 참조 주문, 날짜·창고 선택, 입고·출고 각각의 완료 기준. 로그인 정보는 요청하거나 기록하지 않는다.
3. 우선 연결할 수신 채널 한 가지와 메일 계정 종류 또는 팩스 서비스. 채널별 권한·수신 방식은 별도로 확인한다.

위 자료 확보 후 첫 구현 범위는 원본 → 표준 후보 → 검증·보류 보고서까지다. 합성 자료로 다품목·중복 수신·단위 불일치·부분 납품·정정·합계 오류를 시험하고, 실제 표본과 사람이 대조한 뒤 등록 연결을 검토한다.

## 보관과 현재 결과

원본, OCR 결과, 거래처 코드 대응표, 실제 등록 후보와 화면 증거는 `.local-analysis/`에만 둔다. 공개 저장소에는 설계, 합성 시험 자료와 코드만 둔다. 기존 발주 큐·Firebase·주문 워커에 연결하지 않았다.

대표 명세서의 구조와 보류 사례는 표본 검수로 확보했다. 실제 발주서와의 네 값 대조, 단위·세금·운임 배분 규칙, 진산메디칼 상세 문서 및 대표 미확보 업체 3곳, 실제 등록 절차는 아직 확인이 필요하다. 입출고 등록 도구나 자동 수신 기능이 완성된 상태가 아니며, 필드 대응과 업무 기준도 확정하지 않았다.
